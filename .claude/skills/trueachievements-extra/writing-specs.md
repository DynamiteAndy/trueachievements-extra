# Writing specs

How specs are written here: the recipes and the conventions. The shared helpers, matchers, spec lint rules and the projects are in [test-helpers.md](test-helpers.md); for a spec that fails or crashes, [testing.md](testing.md) first.

## Recipes

- **Waiting in specs:** for a timeout, a wait or a debounce, use fake timers through `useFakeTimers()` from `@ta-x-test` (never `vi.useFakeTimers` by hand; a spec in the `pure` project takes `tick`, `useFakeTimers` and `outcome` from `@ta-x-test-timers`, `test/support/timers.ts`, which imports nothing from `src`), then `vi.advanceTimersByTimeAsync(ms)`, and check the result settled, not how long it took (wait.spec.ts, site-buttons.spec.ts). With no options it fakes timeouts and animation frames (`setTimeout`, `clearTimeout`, `requestAnimationFrame`, `cancelAnimationFrame`); code that reads the clock names its own list (`useFakeTimers({ toFake: ['setTimeout', 'clearTimeout', 'Date'] })`, or `{ toFake: ['Date'], now: new Date(…) }` for a date alone, `['performance']` for `performance.now()`). It puts real timers back when the test ends, failed or not (`onTestFinished`), so call it in the test or its `beforeEach` and write no `afterEach(() => vi.useRealTimers())`. To let a microtask run (mutation records, an awaited lookup), `await tick()` from `@ta-x-test`: never a real `setTimeout` sleep.
- **Fetched pages in specs:** features read fetched pages with `memoizeFetchDocument(url)` (`@ta-x-fetch`), which calls `memoizeFetch` and parses the result. It calls it inside its own module, out of reach of a spy, so a spec that stubs pages through `memoizeFetch` also calls `fetchDocumentsThroughMemoizeFetch()` from `@ta-x-test` (in `beforeEach`), which routes `memoizeFetchDocument` through the spy. Otherwise spy on `memoizeFetch` (`vi.spyOn(taxFetch, 'memoizeFetch')`) and return a fixture per URL. A feature that keeps only what it reads from a page (`memoizeFetchExtract`, for a large page read for a little of it: Hide Owned Items, Highlight Wishlist Items, the giveaway's entry) makes its own MemoizeFetch, so spy on `fetchOk` instead, answering `new Response(fixture)` from a `mockImplementation` (a body is read once), and call `emptyMemoizedFetches()` in `beforeEach`: the real cache's IndexedDB round trip outlasts a tick. Its cache test calls what that returns, to put the real cache back, and waits with `vi.waitFor`. Capture those fixtures from the real fetched page, not the page the feature runs on.
- **Static render or mount:** `renderElement` renders to a static string (no effects, clicks do nothing); a component with state or effects is mounted with `mountForTest(<X />, parent)` (where it goes among the site's markup) or `mountInPage(<X />)` (a container of its own on the page) and clicked with `click(element)` ([test-helpers.md](test-helpers.md) → "Shared helpers"). The page is emptied before every test, so no spec clears `document.body` itself.
- **A feature whose component looks things up in an effect** (show owner progress, the walkthrough preview) has only mounted it when the feature's function resolves: wait for the lookup (`await vi.waitFor(() => expect(…))`) rather than asserting straight after.
- **Writing specs for a component:**
  - Two specs: the **component's** (`<Name>/<Name>.spec.tsx`: mount it with `mountForTest` into the container it really goes in, click or toggle it, check the result with the fixture's real values, including repeating the action and anything the site has that it must leave alone), and the **mounting code's** (does nothing when disabled, on the wrong page, or when its container never loads; adds the component once in the right place among the real siblings; one end-to-end "adds a working component" case).
  - **The exception, the Font Awesome wrappers in `ui/icons`:** they have no spec each. One table, `ui/icons/icons.spec.tsx`, has a row per wrapper (which icon it draws, and the classes it's given); a new wrapper adds a row there. How the svg is drawn is `FontAwesomeIcon`'s own spec.
  - Write the behaviour specs against the **old** code first, so they're shown to test the right thing (below).
  - **Assert how many elements you found before looping over them** (`toHaveLength(3)`, or a `toEqual` on a mapped list): a loop over an empty list passes whatever the code does.
  - **Never end an assertion on an optional chain:** `expect(el.querySelector('.body')?.innerText).not.toBe('')` passes when `.body` is missing. Assert the exact text. The same goes for a table case expecting nothing (`expected: undefined`): `expect(header?.querySelector(…)?.innerText).toBeUndefined()` passes whatever the feature did, so assert the header itself is absent (`toBeNull()`), as the individual-progress specs' `progressOf` does (null for a header the page doesn't have).
  - A component that subscribes in `useEffect` is mounted inside `act()` (Preact runs effects after paint); `useLayoutEffect` runs during the mount.
- **Proving a spec can fail:** `pnpm test:mutate`, which puts the break in memory (SKILL.md → "Rules"), never by writing the old code into the file and restoring it; never `git stash` (on a file staged as new it takes the file out of both the index and the folder: shell.md).
- **Controllers that use elements already on the page** (the walkthrough and manage walkthrough pages) read them on their first render, and only wait for ones that aren't there yet. So a spec can't fake "it never turns up" by mocking `waitForElement` alone: remove the element from the fixture first, then mock the wait so the spec doesn't sit out the 10 s timeout.
- **"Gives the page back exactly" specs:** for a controller that moves or marks site markup, compare the container's `innerHTML` before mounting and after `unmount()`. Removing a class it added leaves `class=""` on an element that had none, so compare with `.replaceAll(' class=""', '')`. A node moved back with `appendChild` lands after the whitespace that followed it: record `nextSibling` and use `insertBefore`.
- **Measuring before and after (Vitest's bench):** put it in a `*.bench.ts` file (only those get the `bench` fixture) and run `pnpm vitest bench <filter> --reporter=default` (it runs in the `page` project only; without the reporter an agent shell prints no figures). `bench` comes from the test context, not an import: `test('…', async ({ bench }) => { await bench('name', fn).run(); })`, and options go second (`bench(name, options, fn)`). For a change: run once with `{ writeResult: './dist/test-results/benchmarks/<name>.json' }` (results must be inside the project; everything in `dist/` but the release scripts is git-ignored, so the baselines stay local), change the code, then `await bench.compare(bench.from('before', thatPath), bench('after', fn))`. Example: [mutation-observer.bench.ts](../../../src/page/mutation-observer.bench.ts).
- **Settings and settings panels in specs:** `setSettings`, `getSettings(<Panel />)`, `shownSettings`, `getAccordions` and `changeSetting` ([test-helpers.md](test-helpers.md) → "Shared helpers"; never `vi.unstubAllGlobals()`: "The Tampermonkey and settings mocks").
- **A page still being parsed:** "The page still loading, and yields" below.
- **A blocked or held-up IndexedDB open:** `fake-indexeddb` models blocking for real, so don't stub `indexedDB.open`: open the same database name yourself and keep the connection (it ignores `versionchange`), then have the service need an upgrade (a store it lacks) for `onblocked`, or start your own `indexedDB.open(name, 2)` first so a plain open queues behind it. Pass the service a time limit rather than faking timers (`fake-indexeddb` runs on them): 1000 ms for a test that must not reach it (`new IndexedDbService(name, store, 1000, retryMs)`), 100 ms only in the test of the limit itself (testing.md → "Flakes under load"). Close your connection at the end of the test. See [indexed-db.spec.ts](../../../src/storage/indexed-db.spec.ts).
- **Specs' `URL` is the real one,** as in Chrome: `new URL('not a url')` throws, so a spec catches code that parses an address without handling a bad one.
- **Code that waits a frame:** fake `requestAnimationFrame` with the timers (`useFakeTimers()`, whose default list has the frames) and run it with `await vi.advanceTimersToNextFrame()`; check first that nothing happened before the frame. With real timers, `await new Promise((resolve) => requestAnimationFrame(resolve))` waits one. The resize observer is stubbed in specs: `stubResizeObserver()` (test-helpers.md).

## Entry specs

- **They check their exact tasks.** An entry point's spec stubs `allConcurrently` (`mockResolvedValue([])`) and checks `toHaveBeenCalledExactlyOnceWith('<batch>', [{ name, task }, …])` with the real task functions imported, so a task left out, renamed or swapped fails, and the tasks themselves don't run (they have their own specs). Checking only that `allConcurrently` was called passes whatever the batch holds.
- **A feature entry point** (an `index.ts` that checks its page and starts a batch) gets its spec from `describeEntry('<folder>', { run, page: () => vi.spyOn(SomeRegex.Test, 'method'), batch, tasks })` (`@ta-x-test`), plus `postsBack: vi.mocked(changeToDefaultStatus)` (with the module mocked to resolve false), `parsed: true` and `bodyClasses` where they apply. Leave `page` out for an entry that runs everywhere (miscellaneous). The batch is stubbed; each task has its own spec.
- **`tasks` must be exact,** so pass each feature into its batch as it is, not wrapped: a feature returning its unmount goes in with `allConcurrently<unknown>(…)`. A wrapper that passes arguments on (tinymce's) gets a test that runs it and checks the arguments.
- **A page script added to `<head>`** (emojis' dropdown toggle) outlives `setHtml`, which resets only `<body>`: remove it in `beforeEach` before counting.
- **To check an entry waits for its batch,** have `allConcurrently` return a promise the test resolves itself (`describeEntry`'s "resolves only once its batch has finished"), and see "Waits, timers and breaking code on purpose" below.

### `src/index.ts`, a module that runs as it's imported

`src/index.ts` starts everything at import, so [index.spec.ts](../../../src/index.spec.ts):
- puts every task in one `vi.hoisted` object, so the `vi.mock` factories and the tests share the same `vi.fn()`s (`@ta-x-features` and `@ta-x-ui` fully mocked, and `./maintenance` (the clean-ups) replaced by its task);
- per test: `mockReset()` every task, set `isGuideSite`, `vi.resetModules()`, then `await import('.')`;
- waits with `vi.waitFor(...)`, as the entry doesn't hand back a promise;
- passes the task's name as `expect(fn, name)`'s message, so a failure in a `forEach` says which task;
- silences `console.error` in the failure tests (the logger reports each failing task);
- checks each task with `toHaveBeenCalledExactlyOnceWith()`: a spec that mocks a task can't catch how it's called, and `allConcurrently` calls tasks with no arguments, so a function with an optional parameter (`runMigrations(list = migrations)`) can't be handed something else again.

Show it fails by breaking the entry with `pnpm test:mutate` (one mutation at a time: a task left out, a failure stopping the rest, the guide site branch also running TrueAchievements').

## SCSS in specs

A `.scss` import in a spec is the compiled CSS, as in the build ([test/plugins/web.ts](../../../test/plugins/web.ts)): the plugin (`enforce: 'pre'`) resolves it to a virtual module `\0ta-x-scss:<path>.js` and compiles it from the file, so `@use` resolves. The id must not end in `.scss`: Vitest's CSS steps blank any such module, even after a plugin's `load` or `transform` returns JS. Stub `GM_addStyle` per test and leave it (never `vi.unstubAllGlobals()`: test-helpers.md).

- **The load path is in two places:** sass-loader's `sassOptions.loadPaths` in [rspack.base.conf.ts](../../../build/rspack.base.conf.ts) and `loadPaths` in test/plugins/web.ts, both `src/scss`. So any stylesheet writes `@use 'variables'`, never `../../`. Change one, change the other: without the build's the build fails ("Can't find stylesheet to import"), without the plugin's, the specs that import a stylesheet do.
- **A spec that needs a stylesheet's CSS imports it** (`import css from '@ta-x-scss/…scss'`): the plugin runs it through sass and then lightningcss's minifier, as the build's loaders do, so it's the CSS that ships. Match it as lightningcss writes it (`:before`, not `::before`; no space before `!important`; media queries as ranges, `(width<=1199px)`), or compare without spaces. Don't call sass's `compile` in a spec: it has no load path.
- **The plugin's lightningcss is the npm package; the build's is rspack's own copy.** They agree today. After updating `@rspack/core` or `lightningcss`, check a stylesheet's spec output is still in a `build:prod` bundle (search the bundle for it; print byte counts, not the bundle).
- **Checking an SCSS change byte for byte** (for the moves): `pnpm run build:prod` is reproducible, so compare `sha256sum dist/local/*.js` before and after (never print the bundle: it holds the author's email). A change meant to keep the output must keep the hashes. Where the CSS is meant to change, compile the three entries (`src/scss/index.scss` and the TinyMCE `skin.scss` and `content.scss`) with sass, `style: 'expanded'` and the load path, into two folders and `diff -r` them; the diff should be exactly the rules you meant to drop or move. A rule moved to another file lands elsewhere in the sheet, so keep its specificity, and compare its computed style live before and after (the installed dev build is the before until you run `build:dev`).

## Elements a spec needs: `find()` (for strictNullChecks)

TypeScript is strict, specs included, so a lookup that may find nothing has to say what happens then. The helpers, through `@ta-x-test` (`find`, `required` and `findByText` in test/support/elements.ts, `elementOf` in test/support/render.ts):
- **`find(selector, root?)`** for an element that must be there. It returns the element or fails the test with "No element matches …" (or "Nothing to look for … in" when the root is itself missing), typed like `querySelector`: a bare tag name gives its element type, `find<HTMLInputElement>('.x')` otherwise. Keep `querySelector` where a test checks it's absent (`expect(...).toBeNull()`), including in a helper some test expects to find nothing.
- **`required(value)`** for any other value that must be there (a helper kept nullable for another test's absence check, a mock's call, an optional callback); it fails the test naming the null or undefined.
- **`elementOf(root)`** for a mount's element (`MountedRoot.element` is `HTMLElement | null`).

A helper some test expects to find nothing returns `X | null` (`(): HTMLElement | null => …`), and its other callers wrap it: `find('a', section())` (`find` takes a missing root and fails), or `required(section()).textContent`.

### Wrapping many lookups by script

- **No TypeScript API for scripts** (tsrs is the only TypeScript installed), so a script can't ask for an error's span. `pnpm exec tsrs -p tsconfig.json --pretty true` underlines each span with `~` under the source line (after any extra message lines; find the line starting with its number). A script can read them to wrap spans in `required()`, in rounds, innermost first.
- **What to convert** (driven by the type check's `strictNullChecks` errors): only a lookup used at once, or a name or helper declared from one that the file never checks for `null`. Check helpers whose head the formatter wrapped onto the line before, and `expect(x.querySelector(…)).toBeNull()` with a single `)`. Skip overlapping rewrites (two errors on one expression produced broken syntax). Back up `src` and `test` first, and restore a failing file from the backup rather than patching the script's output.

## Waits, timers and breaking code on purpose

- **Checking that something hasn't resolved yet: wait a whole `tick()`, not one microtask.** A `Promise.race` resolves a few microtasks after its first promise, so one `await Promise.resolve()` can pass when the code is wrong.
- **A spec about a wait uses fake timers, never the real clock** ("Waiting in specs" above; site-buttons.spec): start the call without awaiting it, `await vi.advanceTimersByTimeAsync(249)` and check nothing happened yet, then advance 1 ms more and check it did. Asserting on `performance.now()` only bounds the wait loosely and costs the real time.
- **To show a spec catches a break**, use `pnpm test:mutate` ([shell.md](shell.md) → "The mutation check").

## Stand-ins happy-dom needs

- **An editor iframe's document:** happy-dom doesn't load iframes (and logs an error for one added to the page), so give a detached `iframe` a document with `Object.defineProperty(iframe, 'contentDocument', { value: document.implementation.createHTMLDocument('') })`, plus `contentWindow` if the code posts to it (toggle-theme-button.spec).
- **`XMLHttpRequest`:** happy-dom's would go to the network. Stub the global with a small `EventTarget` class before a listener starts the interceptor (Vista wraps whichever is global then). Its `status`, `responseText` and so on must be getters: Vista reads them as `super.status`, which an own field doesn't answer (answer with something other than 200, e.g. 201, to see it's read). http-intercept.spec has it.
- **A `<link>` only looked for by its address:** leave off `rel="stylesheet"`, or happy-dom tries to load it.

## Stored values and migrations

- **A new Tampermonkey key must be declared** in [stored-values.spec.ts](../../../src/storage/stored-values.spec.ts) with its owner file, or that spec fails. Only the owner files may call `GM_getValue`/`GM_setValue`/`GM_deleteValue`/`GM_listValues`/`GM_addValueChangeListener` (comments are ignored).
- **A setting's storage key is its path in the tree:** `defaultStatus: setting('game.achievements.defaultStatus', …)` under `game.achievements`, the same dotted path `setSettings({ 'game.achievements.defaultStatus': … })` takes. `settings-keys.spec.ts` fails if the two differ, so renaming or moving a setting (with the folder its feature moves to) changes its key: it needs a migration moving the old key (migrations.ts, as version 5 did for every setting). Properties don't repeat their group, but must still say exactly what they are (the maintainer's rule): `game.forum.overrideForumThreadFilter`, not `gameForumsForumOverride`, a bare `override` (override what?) nor `overrideForumSettings` (which settings?). Name what it covers, from effective-settings.ts, not the menu's looser label.
- **Dropping, renaming or reshaping a stored value needs a migration** in `src/storage/migrations.ts` (next version number, a note, literal keys), with a spec in migrations.spec.ts: old storage in, new storage out. **It must be safe to run twice** (tabs starting together can each run it): a rename copies only while the old key is still there, a conversion converts only what's still in the old form, and the spec's `oldStorage` gets its old storage, as its run-twice check fails without one. Once any migration has run (even one that then threw), `runMigrations` calls `reloadSettings()`, so a migration may rename or convert a `setting()` key: the settings tree, built on import before the migrations, reads storage again. Don't add read-time fallbacks for old formats.
- **A feature's own data:** a small value in Tampermonkey storage is a `stored(key, default)` from `@ta-x-storage` in the feature's folder (the guide links), declared in stored-values.spec.ts with that file as owner; the spec also picks up `stored(…)` keys. Anything that grows (per thread, per page) goes in its own `IndexedDbService` store in the feature, with an expiry (`set(key, value, expiresAt)`), added to maintenance.ts' `expiringStores` so the daily sweep clears it. Every test starts with the script's database empty (`clearScriptDatabase()` in test/mocks/indexed-db.ts clears every store), so a new store needs nothing there.
- **Moving saved data somewhere async** (Tampermonkey to IndexedDB) can't be a migration, as migrations are synchronous: a carry-over in the feature's store module, started by the maintenance task and awaited by the feature's first read (one promise, so it runs once at a time), copying without replacing newer entries and deleting the old key only after every entry is copied (owner-progress-urls.ts). Its legacy key stays declared until a migration deletes it.
- **`GM_listValues()` in specs includes every `localStorage` key,** as the Tampermonkey mock keeps its values there: a feature writing to `localStorage` itself (the sweep's `ta-x:expired-data-swept`) shows up too. Check for the keys you mean, not the whole list, after code that uses `localStorage`.

## Starting before the page has a body

- Everything starts at document-start, so code that needs `<body>` awaits `bodyReady()` (`@ta-x-page`). To spec that, `withoutBody()` (`@ta-x-test`) takes the body off and returns a function that puts it back: start the code, `await tick()`, check what already happened, put the body back, then await it. `setHtml` adds a body if a test left none.

## The page still loading, and yields

- **Use `stillParsing()`** (`@ta-x-test`, test-helpers.md): it fakes a page still loading and returns what finishing the parse does, in one call. happy-dom's document is always parsed, so this models our document-start script.
- **What it does, for a case it doesn't cover:** mock `vi.spyOn(document, 'readyState', 'get').mockReturnValue('loading')`; for a list, take its items out and append them back one at a time as the parser would (the mutation observer sees each); finish the parse with `readyState` set to `'interactive'` and `document.dispatchEvent(new Event('DOMContentLoaded'))`. See [achievements/default-status.spec.ts](../../../src/features/game/achievements/default-status.spec.ts).
- **To spec a wait for the parse:** start the code, `await tick()` and check nothing happened, then finish the parse and await the code.
- `waitForElementWhileParsing()` (in `@ta-x-page`) is what a step uses when it must go before the parse ends. The not-won status fixture (`game-achievements/won-with-dlc-not-won-status.html`) lists a single item: copy it (`cloneNode`, `nw` → `w`) for a won one (default-status.spec).
- An entry that should resolve only when its work is done (so its batch times it): start it while the page is 'loading' and check it hasn't resolved after a `tick()`. Checking the result straight after `await` isn't enough: a dropped promise often finishes within the same few microtasks.
- The list features `await yieldToPage()` (a `setTimeout`) first: a spec that fakes `setTimeout` must do so after awaiting them, or they never start. To spec the yield, check right after calling (before any await) that nothing has changed yet.

## Exact checks

- `toHaveBeenCalledExactlyOnceWith(…)` over `toHaveBeenCalled()`.
- The whole list (`toEqual([...])`) over a length, an `every()` or the first and last items.
- An element's text or classes over `not.toBeNull()`.
- The first run with `toEqual([])` prints the real value to copy in.
- Two `Headers` compare equal whatever they hold, so check a caller's own headers with `toBe`.
- DOM nodes compare by identity everywhere: `toEqual`, `toStrictEqual` and the call matchers (`toHaveBeenCalledWith`…) pass only for the same node, not a look-alike (`test/mocks/matchers.ts`'s equality tester; Vitest's own rule, `isEqualNode`, passes any identical sibling or detached copy). So `toEqual([a, b])` and `toHaveBeenCalledWith(el)` check *which* elements. To compare what two nodes hold, compare their `textContent` or `outerHTML`.
- To check something ends disconnected, compare `mock.invocationCallOrder` of disconnect and observe (mutation-observer.spec's `leftDisconnected`).

## Fixtures: one folder per site page

`test/html/<site page>/<variant>.html` (the maintainer's call): the folder says which page of the site it is, whichever feature's spec loads it, so a fixture shared by several specs has one home and nobody deletes it with "its" feature. The file name says what's special about the capture. Every fixture starts with its capture header (page, date, what was kept or cut), as `pnpm fixture:condense` writes it ([live-site.md](live-site.md) → "Capturing a fixture"); one whose date wasn't recorded says so (`date not recorded`, after the latest date it can't be later than).

- **The site's own pages:** `achievement-page/` (with the site's solutions, without, the old video player, the sub comment box), `achievement-guide/` and `add-guide-page/` (their comment boxes), `game-achievements/`, `game-challenges/`, `game-dlc/` (won, none won, with the Won or Not won status radio), `game-hub/`, `game-videos/`, `game-walkthrough/` (public walkthroughs, as show owner progress and the preview aside fetch them), `games-list/`, `gamer-achievements/`, `gamer-games/`, `gamer-wishlist/` (filtered to what's on sale, as the sales' wishlist highlight fetches it), `forum-thread/`, `forum-thread-list/` (My Threads and a game's forum), `forum-add-post/`, `news-article/`, `sale-article/`, `direct-message/`, `giveaway/`, `home-page/` (the header, signed in and out), `site-toast/`.
- **Staff pages:** `staff-edit-walkthrough-page/` (the image viewer, TinyMCE's parts), `staff-manage-walkthrough/`, `staff-walkthrough-page/`, `staff-walkthrough-preview/`, `staff-walkthrough-page-preview/`.
- **Guide sites:** `xbox-achievements-guide/`, `playstation-trophies-guide/` (with the Cloudflare check at a guide's address), `gamertag-nation-guides/`.
- **Not a site page:** `empty.html` (a page with nothing on it), at the top.
- **Paths in specs** are written out whole (`'@ta-x-test-views/game-achievements/won-with-dlc.html'`), or relative to `@ta-x-test-views/` where a table or helper picks the file (`read('staff-manage-walkthrough/in-progress.html')`); no folder constants that hide which page a spec loads.

## Settings that apply live

A feature whose setting applies live starts on its page whatever the setting, and returns its stop: a spec starts it with `onTestFinished(feature())` (or a `run()` helper doing that), not `await feature()`. Apply a setting live wherever it can be (the maintainer's ruling): a feature with nothing to do on the page yet stays registered and checks again when applied. Make a reload-only setting live only once it's shown to work live.

- **`changeSettingLive(setting, value)`** (`@ta-x-test`): sets it inside `act`, then lets a feature's element wait settle (one `tick`). Use it, not `setSettings`, to change a setting with the page open.
- **`expectAppliesLive(setting, page?)`**: with the feature started and the setting off, turns it on, off and on again; off must give `page()` (the body's HTML by default) back exactly, on again must match the first time. Every live feature has one. A feature that only looks for its element once turned on (Highlight Page Locked Message) needs `changeSettingLive` and `vi.waitFor` by hand.
- **For a feature applied live, `expectAppliesLive` is the two-specs rule's "does nothing when disabled" test:** it starts the feature with the setting off and fails if turning it on changes nothing, so a gate that ignores the setting fails it. Don't write a separate "does nothing if not enabled" test beside it: it's redundant. A live feature whose live test isn't `expectAppliesLive` keeps its off test unless the live test starts with the setting off and checks the page then.
- **Prove the live test bites** (`pnpm test:mutate`): the undo dropped, `.peek()` in place of `.value`, and for `whileSetting` a signal read behind `&&` (a skipped read isn't tracked).
- **Undo exactly:** a class put back where there was none leaves `class=""` (the emoji picker's buttons), and rows put back without the whitespace between them don't match `outerHTML` (auto sort keeps the table body's every node).
- **Components register in `useLayoutEffect`:** a `useEffect` cleanup runs after the next paint in Preact 11, so `applyLive` registered there stayed registered after unmount.
- happy-dom's table body `rows` isn't iterable (Chrome's is): use `querySelectorAll(':scope > tr')`.
- **A component re-mounted gets new ids** from `useUniqueId` (`AskForm`'s field is `ta-x-ask-form-field-<n>`, and `<n>` goes up when a guide site's tab comes back): compare such markup through `withoutUniqueIds(html)` (`@ta-x-test`), which drops the count after each prefix components give `useUniqueId` (a new prefix goes in its list), as the guide tabs', emojis' and show owner progress's live specs do. A live check blanks the number the same way.
- **`act` holds a re-render and its effects until it ends**, so a load a setting change starts inside `changeSettingLive` finishes outside it: load first (the guide sites' links load whatever the setting) or wait with `vi.waitFor`.
