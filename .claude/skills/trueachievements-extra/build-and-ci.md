# Build, release, CI and the bundle

The every-session build rules (always `build:dev`, never `build:release` locally, a header change needs a reinstall) are in [SKILL.md](SKILL.md) → "Commands". This file has the rest: the release path, the CI workflows, bundle analysis and measuring the script's size. The stories behind them: [history.md](history.md) → "Commands and CI".

## Builds and the release scripts

- **Only `pnpm run build:release` writes the tracked release scripts** (`dist/trueachievements-extras.user.js` / `.min.user.js`). `--env release` makes `build/rspack.prod.conf.ts` pick `dist/` over `dist/local/`.
  - CI runs it: the release dist build commits the result to the version bump's pull request, and the tag job builds it again to check that dist before tagging (below).
  - The pre-commit hook unstages and resets any local `dist/` changes.
  - Don't run it locally; `git checkout -- dist` undoes it.
- **The configs are functions:** `build/rspack.prod.conf.ts`'s is async, takes `--env` as `{ release, analyse }` and returns `[prod, prodMin]`, named `prod` / `prod-min` (`analyse` adds Rsdoctor to `prod-min` only, with module concatenation off, written to `dist/local/analyse/`); the dev one (`build/rspack.dev.conf.ts`) takes none. Each variant's header comes from `createMetadata(variant)` in `build/metadata.ts`, written out by its `header()`.
- **The dev and prod configs extend the base with `rspack-merge`** (`merge(baseConfig, {…})`), the maintainer's choice: keep it, don't replace it with object spreads, even though spreads give the same configs today.
- **The bundle targets ES2024** (`target: ['web', 'es2024']`, matching `tsconfig.json`): plain `'web'` compiles to ES5, which is much bigger.
- **Never print the built files' contents:** they carry the author's email (package.json's `author`: in the prod scripts' header, and inside the `package.json` the dev build inlines). Print byte counts, hashes or pattern counts instead. Copying a build file (into `dist/`, or a scratchpad copy) is allowed (the maintainer's ruling).

## CI workflows (`.github/workflows`)

- **`ci.yml`** runs on pull requests, on pushes to `main`, and on a dispatch (`workflow_dispatch`, which the release dist build uses; it tests the branch itself, not the merge with `main`).
  - One run per pull request push, testing the merge with `main`; a newer push cancels the run before it.
  - The push run on `main` gives Codecov the base commit's coverage and test results.
  - **Codecov gets two uploads** from the `test` job, both through `codecov/codecov-action` with `disable_search` and their own file: coverage (`dist/coverage/lcov.info`) and Test Analytics (`report_type: test_results`, `dist/coverage/test-report.junit.xml`). Both run after failing tests too (`!cancelled()`), so a pull request's failing and flaky tests show in Codecov's comment. The separate `codecov/test-results-action` that Codecov's Test Analytics page names is archived; its README points to this one.
- **Its jobs:** `dist-only` first (below), then `lint` (with `--format github`, after the dist check below, then `pnpm install --frozen-lockfile --lockfile-only`: the `node_modules` cache is keyed on the lockfile, so a restored cache would never notice a `package.json` the lockfile doesn't match), `test` and `build` side by side (`build` needs nothing from the other two, so a run whose lint fails still builds; `build:prod-all`: both prod scripts in one process, which still fails naming the variant that broke; on pull requests only, `build:dev` too, a step with an `if:` on the event, so `main` and the dispatched run build only what ships), then `ci`, which always runs and fails unless every job passed. Beside them on a pull request from this repo, `prune-old-runs` deletes the pull request's finished runs (held ones included) on commits before its previous one, keeping this commit's and its parent's, as a dist commit's dispatched run checks its parent's CI (`dist-only`). It holds a token that can delete runs, so it checks out and runs nothing, and `ci` doesn't wait for it, so it can't fail a pull request.
- **`dist-only`** acts only on a dispatched run. When the commit adds nothing but `dist/*.js` (the release's dist commit), its code is the commit before's: it waits for that commit's pull request CI run (`gh run watch --exit-status`) and fails with it, and on a pass `lint`, `test` and `build` skip and `ci` accepts their skips. Any other commit runs every job. On pull requests and `main` it starts and ends at once.
- **`lint` checks a pull request's changes to `dist/*.js`** (checked out with `fetch-depth: 2`, against the merge commit's first parent, the base): it fails when they change and the pull request comes from a fork, or keeps `package.json`'s version. Only the release build writes them, on this repository's version bump, and a change inside one of their long minified lines can't be reviewed by eye. A fork can still edit the step out of its own `ci.yml`, which shows in its file list.
- **Every action from outside the repo is pinned to a commit,** with its version as a comment (`actions/checkout@<sha> # v7.0.1`), as a tag can be moved to other code. Dependabot (`.github/dependabot.yml`) moves them on monthly, grouped (a pull request per directory at most: the workflows', and the setup action's); `workflows.spec.ts` fails a tag. Every workflow also declares its `permissions` (at the top or on every job), as the repo's default token can write; the spec checks that too.
- **Every job sets `timeout-minutes`** (the release workflows' too): 15, and 5 for `ci`, so a hung run can't hold a runner for GitHub's default six hours. A new job sets one too; `test/repo/workflows.spec.ts` checks it.
- **`ci` is the one check `main`'s ruleset requires,** so jobs can be added or renamed without touching the ruleset. A new job goes in `ci`'s `needs`.
- **Every job that installs (the release workflows' too) sets up through `.github/actions/setup`,** which restores the whole `node_modules` from the cache (keyed on `.nvmrc`, the lockfile and `pnpm-workspace.yaml`) and installs only on a miss. A new job reuses it.
- **Releasing:** bump `package.json`'s version in a pull request from a branch of this repository (plain semver: it becomes the tag), add its `## <version>` section as the first in `CHANGELOG.md` (the release's notes; `workflows.spec.ts` fails the pull request when the first heading isn't `package.json`'s version, the maintainer's rule, or has no `- ` notes under it), and merge it once `ci` passes. The dist commit and the tag are automatic:
  - **`release-dist.yml`** runs on pull requests that change `package.json` (`paths`, which looks at the whole pull request, so every later push to it runs it again), not on forks' (their token is read-only), and not while the pull request is a draft (marking it ready for review runs it). When the version differs from the base's, its `build` job (a read-only token) builds `build:release` on the pull request's own commit and keeps `dist/*.js` as an artifact. Its `publish` job (the write token) runs none of the project's code (no setup, pnpm or node: `workflows.spec.ts` checks), fails unless the artifact is exactly the files dist tracks, each a plain file, and, only if they changed, commits them as `github-actions[bot]`, pushes to the branch (never forced: it fails if the branch moved on) and runs `gh workflow run ci.yml --ref <branch>`. A push with `GITHUB_TOKEN` starts no run by itself: the pull request's own workflows show on the dist commit as waiting for approval (`action_required`), and **those aren't to be approved** (the `publish` job deletes them once they show up, waiting up to a minute; `cleanup.yml` catches any it misses), as the dispatch already runs CI there and approving them runs CI and the release build a second time. So that dispatch is what puts the required `ci` check on the new commit (its `dist-only` job skips the rest once the commit before passed); it also means the dist commit can't start this workflow again. A version that's already tagged fails it, as the tag job would never release it. A newer push to the pull request cancels the build before it.
  - **`auto-release.yml`** ("Release") runs on a push to `main` that changes `package.json`, and only when `v<version>` isn't tagged yet. Its `check` job (a read-only token) builds `build:release`, gathers the two scripts and the notes (the version's `CHANGELOG.md` section; it fails without one) and keeps them as an artifact. When `dist/` claims this same version (only 4.0.0, the bridge below), it also **fails unless `dist/*.js` is exactly that build**. Its `release` job (the write token) runs none of the project's code: it fails unless the artifact is exactly those three plain files, then runs `gh release create v<version>` on the commit checked, with both scripts, the notes and `--latest`, which makes the tag too, and fails unless `releases/latest` then names it (GitHub has marked Latest against the flags given before). It never pushes to a branch.
  - **Where installs update from:** `@updateURL` and `@downloadURL` (`build/metadata.ts`) point at `releases/latest/download/<file>`, so every release must be marked Latest. Tampermonkey takes a script from that address: opening it shows Tampermonkey's install page (the maintainer checked, with 3.1.2 Latest). 4.0.0 is the last release committed to `dist/` on `main`: installs from before it read `raw/main/dist`, update to 4.0.0 there and take its new header. **`dist/` on `main` then never changes**, and stays for six months after the v4.0.0 release, so a late updater still finds the bridge (open-items.md).
  - **If the Release workflow fails on dist** (its `check` job): two cases, each with its own error. **dist/ doesn't hold the bridge** (the 4.0.0 pull request was merged without its bot dist commit, so installs from before 4.0.0 would never move): in a pull request that bumps to 4.0.1, put back `release-dist.yml` and `ci.yml`'s release parts (its `workflow_dispatch` trigger, the `dist-only` job, `lint`, `test` and `build` needing it and skipping when it passed, and `ci`'s `needs` and condition) from the commit before their removal (the freeze lets dist change while the base's dist predates the bridge), let the bot commit 4.0.1's dist there, then remove them again in a commit after it, as 4.0.0 did. **dist/ holds 4.0.0 but not this commit's build** (something built into the script changed after the bot's dist commit): bump to 4.0.1 in a new pull request. dist stays as it is, 4.0.1 is released normally, and 4.0.0 installs update to it.
  - In both, only the job that writes holds a write token, and it runs none of the project's code, as the install and build run dependencies' code; within it, only the step that pushes gets the token (`persist-credentials: false` on checkout).
- **pnpm's version comes from `packageManager` only:** `.github/actions/setup`, which every workflow that installs uses, runs `pnpm/action-setup` with no `version:`, as setting one too fails when they differ.
- **The repo's Actions and security settings:** the default workflow token is read-only and Actions can't create or approve pull requests (every workflow declares its own permissions), actions must be pinned to a full commit SHA, and secret scanning with push protection is on. Don't change them without the maintainer's say.
- **`main` has a ruleset** (a branch ruleset on the default branch only): a pull request with `ci` passing (strict: up to date with `main`), no force pushes or deletion, only Admin may bypass. Its pull request rule needs no approvals, but has "require extra approval for unattributed changes" on, which may hold a release's pull request for the bot's dist commit (open-items.md), and code owner review on, with the maintainer the one code owner (`.github/CODEOWNERS`): a pull request changing owned files needs a code owner's approval, even with no approvals required. One the maintainer opens themselves can't have its author's approval, so it merges through their Admin bypass ("Bypass rules and merge"), while a contributor's waits for their approval: the maintainer's choice. Nothing pushes to `main` but a merged pull request; tags aren't under it, so the tag job's push is allowed. Don't change the ruleset without the maintainer's say.
- **Changing the ruleset** (only with the maintainer's go-ahead): read the whole ruleset (`gh api repos/dynamiteandy/trueachievements-extra/rulesets` for its id, then `…/rulesets/<id>`), change only what's asked in a copy, `PUT` the whole body back (`name`, `target`, `enforcement`, `conditions`, `bypass_actors`, `rules`) with `gh api -X PUT … --input <file>`, and read `…/rules/branches/main` after to check every other rule is still there.
- **`cleanup.yml`** runs weekly (and by dispatch) and deletes finished runs older than two weeks, with their logs, and the release bot's runs held for approval (`action_required` by `github-actions[bot]`: the dist commit's pull request runs, so their approval prompt goes too), using a token that can write Actions only. A run held for anyone else (a first-time contributor's, waiting for the maintainer's approval) is never deleted by age (the maintainer's call): **`held-runs.yml`** deletes a pull request's held runs when it's closed or merged (`pull_request_target`, the only trigger whose token can delete a fork's runs; it checks out and runs nothing from the pull request, and takes the branch name through `env`). Reopened, the pull request gets a new run, held again, from `ci.yml`'s own trigger. It never deletes a run still going. It hasn't run yet: it first runs when a first-time contributor's pull request with a held run closes, and a failure shows as a failed run in Actions. Deleting a run also takes its checks off the commit, so a pull request left for more than two weeks needs a new push before it can merge: its `ci` check is gone, and a release's dispatched run fails in `dist-only` once the commit before has no run. Scheduled workflows run only from `main`'s copy, and GitHub turns them off on a public repo after 60 days with no activity. Extra runs are allowed as long as this keeps the list short (SKILL.md → "Rules").

## Bundle analysis (Rsdoctor)

- **Rsdoctor 2** (`@rsdoctor/core`, which holds the rspack plugin since 2.0, and `@rsdoctor/cli`): keep the two on the same version. Both are ESM only, which our TypeScript configs load as they are (`await import('@rsdoctor/core')`).
- `pnpm run analyse` builds the minified release build (`prod-min`) with the Rsdoctor plugin, written to `dist/local/analyse/` so `dist/local/` keeps the script that ships, and keeps its server on port 9988 (`server.port`). Run it in the background (it never exits), and stop the process when done: stopping the shell may leave rspack's `node` process holding the port, so check port 9988 is free after.
  - **Module concatenation is off in this build:** Rsdoctor sizes each module by finding it in the minified output, which it can't do for modules concatenated into one scope. The analysed script is a little bigger than what ships, so its sizes are close, not exact.
  - **No source map:** with one, Rsdoctor sizes almost no module (the cause wasn't found).
- **Comparing two builds (bundle diff):** each analysis replaces `dist/local/analyse/.rsdoctor/`, so the first is kept aside as a snapshot.
  1. On the code before the change: `pnpm run analyse`, stop it, then `pnpm run analyse:snapshot before` (copies the report to `dist/local/rsdoctor-before/`).
  2. After the change: `pnpm run analyse` again, stop it, then `pnpm run analyse:snapshot after`.
  3. `pnpm run analyse:diff` writes `dist/local/rsdoctor-diff.html`, one HTML file with the totals, then Assets, Modules (each module's size in both builds, tagged as new, deleted, changed or not changed) and Packages. It starts no server.
  - For an agent, the same diff as data: `pnpm exec rsdoctor bundle-diff --baseline=dist/local/rsdoctor-before/manifest.json --current=dist/local/rsdoctor-after/manifest.json --json <scratchpad>/diff.json` (`assets`, `modules.added/removed/changed`, `packages`). With neither `--html` nor `--json`, the CLI starts a server and opens the user's browser.
  - **Why a snapshot and not a plain copy:** a report's `manifest.json` names its data files by absolute path. A copied folder's manifest still reads `dist/local/analyse/.rsdoctor`, so after the next analyse the diff compares the new build with itself and shows no change. `build/rsdoctor-snapshot.ts` points the copy's manifest at the copied files.
  - To look at the HTML in the browser pane, serve it from a local port: the pane doesn't open `file://` pages.
- **No MCP server:** Rsdoctor 2.0 removed `@rsdoctor/mcp-server` and its workflow. For questions about the bundle's size, modules and duplicates, read the bundle diff's JSON, or the analysis in the Rsdoctor page while `pnpm run analyse` runs.

## Measuring the script's size

- Rebuild with one thing changed, from a scratchpad config that wraps `build/rspack.prod.conf.ts`'s config function (above), against a fresh baseline of today's code.
- Print only byte counts (`wc -c`, gzip) or pattern counts, never the files (the author's email, above).
- To check the minified build live, or the release build without reinstalling: live-site.md → "Checking the minified build live".

## Building an older commit

For a "before" that is a commit (`HEAD`, or the last full review's): build it in a throwaway worktree in the scratchpad, never by switching this checkout. The worktree gets its own install, so it doesn't touch this checkout's `node_modules` (unlike live-site.md's copy with a junction to them, for a "before" that isn't a commit, where pnpm must never run). `git worktree remove` can't delete its `node_modules` on Windows, so delete the folder and prune:

```bash
cd <repo> && B=<scratchpad>/before && [ ! -e "$B" ] && git worktree add --detach "$B" <commit> && { (cd "$B" && pnpm install --frozen-lockfile --prefer-offline && <build>); s=$?; rm -rf "$B"; git worktree prune; [ "$s" -eq 0 ]; }
```

- `<build>` is what's needed from it, done before the folder goes: `pnpm run build:prod-all && ls -l dist/local` for the prod builds' sizes and compile times (a review's build figures), or `pnpm run build:dev && cp dist/trueachievements-extras.debug.js <scratchpad>/before.debug.js` to keep a dev build for a live before and after (copy it over this checkout's `dist/` file for the "before" loads, then `pnpm run build:dev` here again).
- It stops if something is already at `$B`, deletes the folder only when it made it, and fails if the install or build failed. If it stops because `$B` exists, check `git worktree list`: a worktree this recipe left behind (a killed run) is cleared with `cd <repo> && B=<scratchpad>/before && rm -rf "$B" && git worktree prune` (a new command, so it sets `B` again), then run it again; anything else at `$B`, pick another path.
