# Staff pages (walkthrough team only)

The staff walkthrough pages in [page-map.md](page-map.md)'s Staff table only open for a walkthrough team account, and only for walkthroughs that account can open or manage: the ids for this developer's account (a walkthrough they can edit and its page ids, edit page id pairs, one covering several games, ones they can't manage) are in local.md → "Walkthroughs this account can open or manage". Below, `<id>` is such a walkthrough and `<page id>` one of its pages.

## Reaching each page, and which walkthroughs to use

- **Reaching each staff walkthrough page in the state a check needs:**
  - **Walkthrough page with a page selected** (the page history *and* the preview, `#chWalkthroughPagePreview`, side by side): `/staff/walkthrough/walkthroughpage.aspx?walkthroughid=<id>&walkthroughpageid=<page id>`. Both parameters are needed: `?walkthroughpageid=<id>` alone redirects to the manage page.
  - **Walkthrough page with no page selected** (the page history only, an empty version list, **no preview**: the site doesn't render one): the same with `walkthroughpageid=0`. A missing preview there is the site, not us.
  - **Other pages of a walkthrough:** the page history's "Page" dropdown (`select` with `onchange="Postback('sddWalkthroughPageID','')"`) lists every page as `<option value="<page id>">`: read the ids from it and open the URL above with one, rather than changing the dropdown (a postback).
  - **Manage page with a walkthrough selected** (the achievements, games and gamers panels, the table links): `/staff/walkthrough/managewalkthrough.aspx?walkthroughid=<id>`. Without `?walkthroughid` it shows the walkthrough list. A long walkthrough for the table links' timing: **1418**, Halo: The Master Chief Collection's, whose public page lists all 700 of the game's achievements (its public page `/game/Halo-The-Master-Chief-Collection/walkthrough` carries `walkthroughid=1418`); only its team can manage it (for an account that can't, the manage page ignores the id and shows only the walkthrough list).
  - **Edit page** (TinyMCE; read-only checks only, it autosaves): `/staff/walkthrough/editwalkthroughpage.aspx?walkthroughpageid=<page id>&walkthroughpagecontentid=<content id>`, both needed. The content id isn't in the walkthrough page's markup: its "Edit page" button is a postback (`Postback('btnEditPage2_click')`), so don't click it to find out (it opens the edit page, which autosaves). Use the known pairs in local.md, or ask the user for a page's edit link.
  - **Manage page with a page selected** (`#divEditPage`). No URL selects a page (`&walkthroughpageid=`, `pageid`, `wpid`, `page`, `walkthroughpage`, `selectedpageid` and `pid` are all ignored), nor does the walkthrough page's "Back to management" (a postback back to the manage page with no page selected), nor a click on a `#lstWalkthroughPages` row (no link or `onclick`, no script mentions the list; a click alone gives no postback and no page panel). **The way in:** click **Add page** (with the user's OK each time: it changes the page's server state, though nothing is added and the Pages count stays the same); the rows then become editable. Read, then leave by navigating to the manage page's address, without Save or Cancel. What it shows, on unpublished and published walkthroughs alike: one Ready for review (ours, first in the site's row), and our missing buttons (Add page, Preview, View and edit content) between the page panel and the site's buttons. Our container and action row don't mount there, by design (no side panels or Action menu: `#divWalkthroughHolder` holds only the list and the edit panel). Fixture: `staff-manage-walkthrough/page-selected.html`. An existing page selected: open-items.md.
  - **Walkthrough preview:** `/staff/walkthrough/walkthroughpreview.aspx?walkthroughid=<id>` (its side column filled for a walkthrough the account can open; its page links are `walkthroughpagepreview.aspx?…`).
- **A walkthrough covering several games:** its manage page's "Games in this walkthrough" (`#lstWalkthroughGames`) lists them, and games that share one name (several "Xbox 360 Team" sets do) are the case to check the games table's links with (each game once). The manage table's game rows carry only the name (no id or link) and aren't in the preview's order. local.md names one the user can manage, if any.
- **The address can name another walkthrough than the page shows:** picking a walkthrough in the manage page's list (`Postback('lstWalkthroughIDE','<id>')`, a click or Auto Select First) posts the form back to the page's own address, so the address keeps the walkthrough it was opened with while the page shows the one picked (its Name, its selected row, its games). A load by the address always shows that address's walkthrough. So read the Name field first (`input[id*="Name"]`) and only trust the panels when it matches, and our code takes the walkthrough's id from the selected row, never from the address (the table links do). A pick is a postback that doesn't save.
- **The list's post backs may be made for a check without asking** (the maintainer's ruling): the status filter (`#ddlStatusFilter`, which Default Status changes) and a walkthrough picked in the list (which Auto Select First clicks). They filter and select; nothing is saved. Turning Default Status and Auto Select First on for a check is changing our settings (live-site.md → "Changing our settings for a check"). Every other post back on staff pages still needs the user's OK (Add page, Edit page, anything that might save).
- **Checking Default Status with Auto Select First:** open the manage page without `?walkthroughid` and with no status selected, both settings on. Default Status posts the filter back and the rest of the page's work stops; the page that comes back has its status selected, so Auto Select First picks that list's first walkthrough. What happened across the loads is gone before `javascript_tool` can look: use a temporary `sessionStorage` probe (live-site.md → "Seeing when our code ran during a navigation") and `read_network_requests` (→ "Counting page loads and posts").
- **The preview's background reads don't move an open manage page:** to fill its side column, a walkthrough preview GETs that walkthrough's manage page and POSTs its form (a 302 to the public page). A manage page already open in another tab still acts on its own walkthrough afterwards: a postback there (sorting its achievements) kept its Name, achievements and games, and so does a fresh load by URL.
- **Still to check live:** see [open-items.md](open-items.md) (a long walkthrough's table links, two games' achievements, an existing page selected on the manage page).
- **Walkthrough previews to check with:** #BLUD (4138; page 3 is `pageid=26660`) is the walkthrough the specs use. For an account that can't open it, its manage page answers with the walkthrough list, so the feature removes the side column there, as it should: a good check for that case. To see the column filled, use a walkthrough the user can open (local.md): `walkthroughpreview.aspx?walkthroughid=<id>` (thanks and achievements) and `walkthroughpagepreview.aspx?pageid=<page id>` (pages, thanks and achievements). Its manage page (`?walkthroughid=<id>`) works for the manage walkthrough features too.

## The staff features' states and checks

Manage walkthrough's table links: `ManageWalkthroughTableLinks` (under `ManageWalkthrough`) renders `TableLinks` while the setting is on (it applies live: turned off, `TableLinks` unmounts). `TableLinks` owns `preview` (the selected walkthrough's preview page, fetched) and `achievementLinks` in `useState`s, switched with Preact DevTools. Unmounting it puts the cells, rows and total back.

Walkthrough preview: `PreviewAside` (its own folder in the feature) owns `{ status, walkthrough }` in a `useState`, switched with Preact DevTools the same way as show owner progress (from the console, walk up from one of the aside's sections). To look the walkthrough up again, reload; to look up another, switch to `ask` and type its id in (one the user can open, local.md). For an account without access to #BLUD, its previews go without our aside ("Walkthrough previews to check with" above).

Checking anything stuck under the header live (the edit page's toolbar, the walkthrough page's page history; `stickUnderHeader` in `page/sticky`): pinning at the container's end needs a short window (about 450px tall) on both pages, or the page ends first (scroll and frame rules: live-site.md → "Scrolling to check the sticky header").

**Edit walkthrough sticky toolbar** (`StickyToolbar` → `stickUnderHeader`, shared with the walkthrough page's page history, which follows the header the same way, 5px under it):
- In place: `static`, over the site's inline position (`!important`), so the site's own `StickyToolbar()` no longer decides when it sticks (site-quirks.md → "Sticky header and scrolling"). Stuck (`ta-x-sticky-under-header-stuck`, `position: fixed`) from when the editor's top goes under the header's bottom (wherever the header is, mid-slide too) until the editor's bottom leaves the window. A spacer (`…-spacer`) holds its place. Sticking only once the editor's top is under the header means it's never moved clear of the header while in place (`applyStickyElementStyle` takes `stuck` for an element its owner has stuck under the header with its container still in view; a transform that moved it clear trailed the header and the page).
- At the editing area's bottom: pinned (`…-at-end`, `position: absolute`).
- It slides with the header (a copy of the header's own slide; `ta-x-y-show` / `-hide` follow the header's). It's placed again on scroll, on editor resize, and a frame after the header resizes.
- It follows the header's class as well as the scroll (`mutationObserver.onAttributeChange(header, ['class'], …)` in `stick-under-header.ts`): a change of the header's show / hide class that comes from a Preact render rather than from the scroll lands after the scroll listeners have run, so a listener reading it on the last scroll would see the previous state.
- To drive it: scroll with the pointer at the page's edge (over the editor the wheel scrolls TinyMCE's iframe); narrow the editor with a temporary `max-width` on `#divEditWalkthroughPage`; change the header's height by hiding its promo bar with a temporary style (not its ✖). If the page doesn't scroll, append a temporary 2500px div after `.admin-page`. Step `window.scrollTo` a frame or two apart, logging each frame, to see a flip or a jump.
- Check: the toolbar's top = `Math.max(header.getBoundingClientRect().bottom, 0)` once the 0.5 s slide has settled.

**Walkthrough page's sticky page history** (`StickyPageHistory` → `stickUnderHeader`), the same in dev and release builds (a short window, real wheel scrolls): header hidden: the history fixed 5px from the top; header shown: 5px under it (55); at its container's end: pinned there (`at-end`, absolute, 10px above the container's bottom), staying pinned when the header comes back.

Checking the edit walkthrough autosave notification: it is off by default and applies live, so turning it on in the settings menu is enough, with no reload (local.md says whether the user keeps it on). Edit pages the user can open are in local.md (edit pages: SKILL.md → Rules; one for a walkthrough they can't edit redirects home). The site autosaves (`$.ajax` to `/ajaxfunctions.aspx/AutoSave`) on load and then every 30 s, so sample the toast for about 35 s.
