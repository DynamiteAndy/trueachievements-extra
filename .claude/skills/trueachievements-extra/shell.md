# Shell habits: Bash, git, scripts and file moves on this repo

Read this before running scripts that edit files, moving files, or proving something with the mutation check. SKILL.md keeps the few habits every command needs.

- **Start every Bash command with `cd <repo> &&`** (the repo's Git Bash path, in local.md) or use absolute paths: a bare `cd` into a subfolder carries over into later commands.
- **Git:** `git mv` / `git rm` **stage** their changes; commit only when the user says to, and say what's staged. After a piece of work's change review (repo-review), or a verification pass of applied fixes, ask: a new commit or an amend on the current branch, or a new branch when on `main` (never a commit to `main`). `git mv` only works on tracked files (much of the work is untracked: move those as they are rather than `git add` it all). `git rm` refuses a file staged as a rename (`has changes staged in the index`); if it's unchanged from `HEAD`, `git rm -f` is safe. **Never `git stash`, not even one path:** on a file staged as new it takes the file out of both the index and the folder. To compare with an older version, copy the file aside (`cp`) and back.
- **Line endings are LF everywhere** (`.gitattributes` `* text=auto eol=lf`, which wins over `core.autocrlf=true`). A CRLF file written by some tool: `oxfmt --write <file>`.
- **Windows paths are case-insensitive** (CI may not be): no file and folder differing only by case (components.md → Folder layout).
- **A write can be refused for a moment, cause unknown** (errno -4094 `UNKNOWN`; oxfmt's "a file with a user-mapped section open"; Python `OSError: [Errno 22]`). It happens on Windows, most often straight after `git mv` (to tracked files written right after the move; never seen on untracked files moved with `fs.renameSync`), but also on files nothing had touched for hours. Every write went through on a retry, and whatever holds the file lets go within about 2 s, too soon for a handle list taken afterwards. So:
  - **Investigate before retrying, and say "unknown", not "likely X"** (Defender, the desktop app or an editor are only guesses). In the failing script or straight after: note the time (UTC) and file, list what's running (`Get-CimInstance Win32_Process`), retry with a log of how long until the write goes through, and record it in local.md's log.
  - **Every scripted write goes through a helper that catches a refusal** and runs the machine's handle tool at once, if local.md names one (its write-or-catch helper). Without one, ask the user before installing anything, and never change Defender. A non-admin handle list may not see system processes' handles: if it finds nothing, say so rather than conclude.
  - **A script that `git mv`s and then writes retries a refused write** (500 ms apart, up to 10 s), or writes before moving; keep a retry in any script that writes source files, and read each write back. (Breaking code to prove a spec is never a script: `pnpm test:mutate`, below.)
  - The incidents behind this: [history.md](history.md) and local.md.
- **Scripts with quotes, template literals, regexes, backslashes or Markdown backticks:** write them to a file in the scratchpad with the Write tool and run `node <file>`. **Never put them in `node -e` or a heredoc** (`node - <<'EOF'`, `cat <<'EOF'`): those mangled them again and again (lost backslashes, failed parses, backticks run as commands). Fix a script with the Edit tool, not `sed`; plain `sed -E` with the pattern in single quotes is fine for a one-line swap across a few files.
- **Back up `src` and `test` to the scratchpad before a script edits many files** (`cp -r src test <scratchpad>/backup-<time>/`): hundreds of files are untracked, so git can't put one back. From Bash, don't back up to `/tmp`: Git Bash's `/tmp` isn't the scratchpad, and a scratchpad path that doesn't exist makes the restore `cp` fail silently in a `;` chain.
- **A rewrite script** makes exact-string replacements that must each match once (a helper that throws otherwise), not broad regexes (a lazy `[\s\S]*?` between markers runs on into the next block; `(?:(?!describe\()[\s\S])*?` keeps it inside one). Count matches against what you expected, and write a file only once all its replacements matched.
- **Check a command before handing it to the user:** check its paths and quoting, and run whatever can run unelevated yourself first; give the user only what really needs them (elevation, their real environment).
- **Chain dependent steps with `&&`.** After a failed script, `; pnpm vitest …` runs the specs against the unchanged files (or from the wrong folder) and looks like a result.
- **The mutation check** (the maintainer's choice over Stryker): `pnpm test:mutate <experiments.json> [id]` ([test/tools/mutate/prove.ts](../../../test/tools/mutate/prove.ts), its in-memory transform in [test/tools/mutate/vitest.mutate.config.ts](../../../test/tools/mutate/vitest.mutate.config.ts)); nothing in the repo is written. Use it for every "prove it" (spec reviews, dead code) instead of a new script.
  - **The experiments file** (keep it in the scratchpad) is a JSON array of:
    - `{ id, kind: 'mut', spec, muts: [{ file, from, to, line?, nth? }], cand: [{ file, line, name? }] }`: break source lines: does each candidate fail, and what else fails? A `test.each`'s rows are reported at the line of the test's body, not of `test.each(`, so name a candidate by part of its title (`name`, matched against the full title, describes included; `line` is then only its label) rather than guess the line; a candidate that matches nothing shows as `NOT FOUND`.
    - `{ id, kind: 'cov', spec, skip: [{ file, line }], sources }`: skip tests: what coverage is lost?
  - **Results** go beside it as `results-<name>.json`, each run's Vitest output in `<name>-runs/` beside it too, so sessions running at once (each with its own experiments file, in its own scratchpad) never read each other's. A mutation that doesn't apply fails loudly (`MUTATION NOT APPLIED` / `AMBIGUOUS`: add `nth` or `line`). `nth` counts from 0, on its `line` when both are given, and one past the last match fails; `to` goes in as written (no `$&` replacement patterns). A mutation whose `file` no spec loads reports `MUTATION NOT APPLIED: no spec loaded <file>` in its `err`.
  - **Unhandled errors count as a catch:** a test that passes but leaves an unhandled error (Vitest's "Unhandled Errors", which fail a plain run) gets the status `unhandled` (put down to the last test that ran before it); `unhandled` lists them all.
  - **So do a crashed worker and a run that times out:** a spec file that failed with none of its tests failing (its worker exited, as a break that loops until memory runs out does, leaving its tests `pending`; or its `beforeAll` threw) is listed as `<file>:0 (file failed) …`, and a run over 10 minutes is stopped and listed as `(run):0 (timed out …)`. Its candidates show `pending` or `NOT FOUND` then, so read `othersFailed` too.
  - **A test is redundant** when skipping it loses no coverage and every break it catches fails another test too.
  - **Code is unused** when breaking it fails nothing in the whole suite (and the break compiled). Count a break as "did not compile" only on a failed suite or transform: a `SyntaxError` a test hits at run time (a `JSON.parse` of a broken stored value) is a real catch.
- **Moving files:** a script takes a plan of `[from, to]` (files or folders), dry-runs first, `git mv`s what git tracks wholly and renames the untracked rest, then rewrites every relative import, `export … from`, `vi.mock` and `import()` in `src` and `test`: resolve the specifier against where *both* files were before, and write it relative to where both are now. Write it again from this when needed. Then by hand:
  - **Name clashes across kinds:** match a moved file only with the same extension (a `.scss` beside a `.tsx` of the same name made the `.tsx` look moved too).
  - **Barrels:** drop the moved names from the old folder's `index.ts` (e.g. `ui/index.ts`, a feature's `index.ts`), give the new folder an `index.ts`, and have other features import through it; the type check lists every name still read from the old place, and every class name still read through an object it left (`styles.ts` objects are `as const`).
  - **Long `../../../../` paths:** use the alias (`@ta-x-ui`, `@ta-x-page`), exporting from the barrel what a moved file needs (`classNames`, `FontAwesomeIcon`), then merge the duplicate import lines.
  - **Stylesheets:** a moved one keeps `@use 'variables'` (the load path); the index that pulls it in uses a relative path at the same position, and gives two files of the same name their own namespace (`as games-collapsible-groups`). Prove the CSS byte for byte (writing-specs.md, "Checking an SCSS change byte for byte").
  - **Aliases:** rspack, Vitest and `test/support/fixtures.ts` read tsconfig's `paths`, so dropping one is one line there. Imports through an alias (`@ta-x-scss/…`) aren't rewritten by the script: grep for the old path.
  - **Class names and CSS variables moved between objects:** specs read them through the same object as the code, so a mistyped string passes; only the SCSS catches it. Check live that each moved class is on its element and each variable is set and read, or compare the strings against the old file.
  - **Afterwards:** rename `describe` blocks to the new path, update the `owner` paths in stored-values.spec.ts, and grep the skill files (and any planning notes) for the old path.
- **Reading or rewriting fixtures with a script:** Node has no `DOMParser`, but the project's `happy-dom` works from a script anywhere: `const { Window } = require('node:module').createRequire('<repo>/package.json')('happy-dom')`, then `new Window().document.write(html)`.
