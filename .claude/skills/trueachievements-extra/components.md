# Writing components (Preact)

Every piece of our UI is a Preact component. These are the conventions for any new or reworked component. Specs and fixtures: [writing-specs.md](writing-specs.md) and [live-site.md](live-site.md) → "Capturing a fixture".

## State

- **Components keep their own state.** `useTabs` / `useDragScroll` for tab groups, `useCollapse` for collapsing content. Never add a document-level delegated listener or an event bus for a component's own behaviour.
- **A tab panel most visits never open is `lazy`:** `<TabContent lazy>` builds its children the first time it shows and keeps them. Children that cost something to work out go in as a function (`{() => items.group(index)}`), so they aren't even worked out before then. Don't keep your own record of opened tabs (the settings menu and the emoji picker both use this). A panel inside something closed (a menu) passes `visible` only while that's open, so it isn't built while closed.
- **Markup the site owns gets a controller component** (the self-contained components rule). It's handed the site's element, keeps the state, applies it to the element in an effect, and renders only our parts, through `createPortal` or `mount()` into the site's cells. Never re-render the site's own nodes: its scripts move them (the sale tables' sort). It **gives everything back as it was on unmount**: classes it added, nodes it moved (record `parentNode` and `nextSibling`, put back with `insertBefore`), text it changed. Examples:
  - `HideableRow` (`hideRow()`): one site row;
  - `StickyHeader`, `StickyPageHistory`, `StickyToolbar`: a site element and its scroll listener;
  - `ImprovedImageSelector`: the site's popup, which only the site opens;
  - `ManageWalkthroughTableLinks` (rendered by `ManageWalkthrough`): portals a link into each site cell (the cell's own content set aside and put back on unmount), the missing achievement rows into the table's body, and the count into the list's total;
  - `WalkthroughPage`, `ManageWalkthrough`: a whole page's layout;
  - `IndividualProgress` (the site's group headers' text) and `HoverableParagraphs` (a class on the walkthrough page's text): controllers that render nothing of their own, mounted detached (`mountDetached`).
- **Prefer a controller even when the gain is small:** feature code that keeps a site element in module variables with listeners added once becomes a controller component with its listeners in `useEffect`, so every feature matches. Plain DOM stays only where Preact can't reach: moving the site's own nodes, and scripts injected into the page (TinyMCE).
- **A page controller uses elements already on the page from its first render** (`useState(() => root.querySelector(…))`) and only waits for the ones that aren't there yet. Effects that use them then run while it mounts, before the page's other tasks read what they change (waiting a render later breaks any task that reads the page straight after).
- **One sender and one listener in the same feature usually means one job split in two** (the maintainer's rule). Merge them into one module that does the steps in order, rather than keeping an event between them. Files that each do something independent (TinyMCE's buttons) stay separate.
- **State set from outside a component goes in a signal** (`@preact/signals`, the maintainer's choice): a module exports the signal and a setter (`toastMessage` / `showToast` in `src/ui/toast/toast-message.ts`). The component reads `.value`, which re-renders it on change; a value set before it mounts just waits. Use props for everything else, and a plain call (not a signal) for a one-off action between two parts of a feature. A signal that would leak between tests is reset for every test in `test/mocks/page.ts` (as `toastMessage` and `settingsMenuOpen` are), not in each spec.
- **State shared by two roots** (the settings menu and its wrench, mounted in different places) is a signal both read: `settingsMenuOpen`, exported from the settings menu's index. Don't re-render both through `mount().render`.
- **Settings are persisted signals** (`settings` in `@ta-x-storage`): each a `setting(key, default, storedAs)` that saves to Tampermonkey storage and follows other tabs. Features read `settings.….peek()` (or `effectiveSettings`, `storage/effective-settings.ts`, for the ones that inherit until their override is on); components read `.value`. A storage key never changes without a migration: `settings-keys.spec.ts` lists them all.
- **Settings menu rows take the setting itself:** `<CheckboxSetting setting={settings.…} />`. A row that depends on another setting is rendered only while that holds (`{override.value && …}`). The row saves through `saveSetting`: lint's `react(immutability)` refuses assigning a prop's `.value` in a component, so don't inline it, however thin it looks. Code that holds a setting itself, not as a prop (the edit walkthrough's theme toggle), assigns `.value`. Specs use `setSettings`, `getSettings` and `shownSettings` from `@ta-x-test`.
- **Settings row props:** helper text about a toggle's own state goes in `helperTextWhenChecked` / `helperTextWhenUnchecked` (an override's "Some settings will be inherited…" is the unchecked one); plain `helperText` is for text that depends on something else. Every settings component calls its row classes `containerClasses`, from `settingRowClasses` (`@ta-x-ui`, `src/ui/settings/setting-row-classes.ts`), never a raw `ta-x-hide-…` string. They only say how a row sits in a toggle's group:
  - `noBorderWhenChecked`: a toggle whose rows show while it's checked (no line below while checked);
  - `underToggle`: a setting under the toggle that reveals it (no gap above);
  - `underToggleNoBorder`: the same, with more of them after it and no line between;
  - `underToggleNoBorderWhenChecked`: a setting under its toggle that reveals rows of its own while checked.

  **The lines follow the site's gamer menu** (the maintainer's ruling): one under every row and group header, a group's last row and the row above a header included; none inside a toggle's group; none under a tab's last row. The stylesheet draws the ones a row's place calls for (a group's last row, the row above a header, a tab's last row) whatever its classes, so no panel says them. `settings-menu-lines.spec.tsx` mounts the whole menu, every setting on and then off, in both themes, and fails on any row whose line breaks the rule. It also compares the menu with every setting off and on: each row that shows only while a toggle is on is a revealed row, and must carry `underToggle` (or one of its variants), so a revealed row left unmarked fails too. A dropdown with no option row of its own above it takes a `label` (`SelectSetting`). The rules for these classes, and for the rows and their helper text, are in `src/ui/settings/_settings.scss`; the settings menu's stylesheet keeps only its own layout.
- **The settings menu's layout** (`settings-menu.scss`): every tab keeps the scrollbar's room (`scrollbar-gutter: stable`), so controls sit 25px from the edge whether a tab scrolls or not, and every view's content starts 10px in. The Feature Documentation view is laid out as blocks with each gap set once: 20px before a setting (`h3`), 5px under it, 10px between paragraphs and lists, 10px around a group band (`h2`, `box-sizing: border-box` so it ends where the text does). List text is 14px in the docs, changelog and credits alike. Keep a settings row's helper text to a line or two; the detail belongs in FEATURE-DOCUMENTATION.md.

## Every state checkable live (the maintainer's rule)

If a component has states (loading, ask, loaded, shown, hidden…) or only appears after an event (a save, an ajax response), a dev build must be able to switch between them.
- **State a component owns** (its `useState`, a signal) is switched with Preact DevTools (page map → "Switching states"). So a state worth checking lives in a component, not in a module variable.
- **No dev console commands** (the maintainer's ruling): don't add `listenForDevCommand`, `ta-x:<feature>` events or any other console or `CustomEvent` hook. To check a state live, move it into a component, so DevTools reaches it. What DevTools can't switch (a lookup, a toast built from a response) is checked by its real trigger on the live page, and by its spec.
- **Drive states through the component's own state, not the DOM.** A component holds its states in `useState` (or reads a signal) and renders from them. Never remove elements by selector or toggle classes to switch state (the maintainer rejected it). Don't give a field a `value` prop unless it's controlled: re-rendering resets what was typed.
- **Spec it:** every state the component can show.

## Folder layout

Features sit in the folder for the page they run on (SKILL.md, "Where code goes": `/games.aspx` → `src/features/games-list/`). Each component gets its own PascalCase folder next to the kebab-case code that mounts it:

```
src/features/<area>/<page>/<feature>/   (e.g. game/walkthrough/hoverable-paragraphs/)
  add-thing.tsx                 ← mounts it: setting and page checks, then mount()
  add-thing.spec.tsx
  styles.ts                     ← class names shared by the component and the code mounting it
  ThingButton/
    ThingButton.tsx             ← named export only
    ThingButton.spec.tsx
    index.ts                    ← export * from './ThingButton';
```

- The component imports `../styles`.
- **Never give a file the same name as a component folder beside it, ignoring case** (`snackbar.tsx` beside `Snackbar/`): Windows paths are case-insensitive (CI may not be), so `./Snackbar` resolves to the file and Preact renders `[object Object]`. `test/repo/project-structure.spec.ts` fails the run if it happens in `src/`.
- Sub-components and hooks go inside the component's folder. Components used by more than one feature go in `src/ui/<kebab-name>/` (`src/ui/tabs/`, `src/ui/hideable-row/`), which holds the PascalCase component folder(s) in the shape above (`TabBar/`, `TabContent/`, `TabLink/`), a `styles.ts` and a `_<name>.scss` partial.
- **Exports:** components, helpers and utilities use named exports only, no `export default` beside them. The exceptions: a feature's entry point (`export default async () => …`, imported by its page's or area's `index.ts` as `import sales from './sales'`), and `styles.ts` / `attributes.ts`, whose default object is what gets imported. Import components from the `@ta-x-ui` barrel, never a deep path (there's no `@ta-x-ui/*` alias any more). Don't name an export after a global it shadows: the throw-on-error fetch is `fetchOk`, the bubbling event helper `triggerEvent`. Export a type (a component's `Props` included) only when another file imports it (the maintainer's ruling).
- **A read kept only for its effect** (subscribing to a signal, forcing a layout) isn't written as `void x.value`: lint's `no-meaningless-void-operator` allows `void` only before a call. Use the value (`const [on] = [a.value, b.value]`), assert it in a spec, or call something (`getBoundingClientRect()`).
- **Keep a feature's own state and flow in the feature** (self-contained features); code two features genuinely share goes in one copy (SKILL.md, "No duplicate code, even for two users"). Code mounting a component becomes `.tsx` (`git mv x.ts x.tsx`).
- **Facts about the site that several features need go in `@ta-x-site`, not in one feature that others import:** the site's smileys and controller buttons (with their sizes and picture paths) are in `site/images.ts`, used by the emoji picker, the walkthrough editor's controller menu and the guide cleaner. A page function can't import them, so pass them as an argument.

## Conventions

- **Extend a shared component rather than opting out of it** (the settings menu uses the tabs component, not tab state of its own).
- **Names say what they are,** shortened or not: dropping a repeated prefix is good, but not down to a bare generic word (`override`, `value`, `enabled`, "settings": override what?). Ask whether the name would still be clear if another feature in the same group had the same kind of thing, check a whole rename list for generic words before applying it, and say which names you kept and why (writing-specs.md → "Stored values and migrations" for settings).
- **A default that applies only when the user arrives** (a default status, filter or tab) checks `isFreshArrival()` (`@ta-x-page`): the site's filters post the page back to its own address, and a reload counts as staying, so the user's own pick then sticks. The exception is a page that marks the user's pick itself (the manage walkthrough page's status filter renders the picked option `selected`): read that, as it's exact where the referrer is a guess. Code that should act after a post back (a cached copy the change may have made stale) uses the same check the other way round.
- **Mirror the site's own version.** When the site renders its own version of a control (its `#btnReadyForReview`, its walkthrough aside rows), compare against it live and follow its markup, icons and attributes.
- **Removing a "dead" CSS rule is a look change.** A few sample widths looking the same proves nothing about the bands between them, and specs can't see layout (happy-dom lays nothing out). Test each edge the rule guards: just above and below each breakpoint it names, including within a scrollbar's width (site-quirks.md on `.middle`), comparing `document.documentElement.scrollWidth` with `clientWidth` and the element's width. Reproduce what its old commit or changelog says it fixed. If you can't show it's harmless there, keep it with a comment saying what it guards.
- **Matching a site look** (e.g. its `$.toast`): trigger the site's version live, capture its markup, classes and timing, and render the same markup and classes so the site's CSS styles it. Don't copy the CSS. Check the CSS is really loaded where the component appears, and add our own only for real problems. [site-looks.md](site-looks.md) has the closest match for each look.
- **Fix bugs you find on the way** (the maintainer wants them fixed, not just noted), with a spec that fails without the fix (proven with `pnpm test:mutate`, SKILL.md → "Rules"); if the fix changes something the user can see, confirm it's a bug with the maintainer first (SKILL.md → "Ask before changing a look or behaviour that's visible").
- **Refactor as you go** when it's small and covered: finish each piece of work with a quick look for duplication it exposed, and check the real code before proposing a shared component (look-alike controls may mirror different site markup). Before refactoring an item, check its file's coverage and add specs from real site fixtures first; fix the likely bugs first.
- **Behaviour lives in the component that owns it:** a single-use component keeps its own handler (a module-level function wired to `onClick`). The mounting code only does the setting and page checks and `mount()`. Take a handler as a prop only when the component is reused with different behaviour.
- **Listening to the site's responses** (`httpIntercept.onResponse`, `@ta-x-fetch`): listeners are synchronous and read-only, `(event: { req: Request; res: Response }) => void | boolean`; nothing can change a response. A `once` listener is removed as soon as it returns anything but `false` (or throws), and a listener unregistered while a response is going through the listeners doesn't run for it. A listener that needs the body reads `res.clone().text()` without awaiting it inside the listener.
- **The resize service tells a late listener nothing** (`page/resize-observer.ts`): it observes an element once, so a second listener registered later for the same element gets no first notification of the size it has. Read the size yourself when you start listening.
- **Mount with `mount(<X />, parent, before?)`** from `@ta-x-page`, which returns `{ nodes, element, render, unmount }`. Never call Preact's `render()` straight into a site element: it takes over every child. (A controller with nothing of its own on the page mounts with `mountDetached(<X />)` from `@ta-x-page`, a root of its own off the page, which returns `{ render, unmount }`.) Specs mount with `mountForTest` or `mountInPage` from `@ta-x-test` instead, which unmount when the test ends (test-helpers.md).
- **Code that has to run in the page itself** (TinyMCE's editor, the site's jQuery and functions) is a *page function*: an ordinary typed function injected as its own source with `createPageScript(id, fn, args)` from `@ta-x-page` (page/page-script.ts). It's minified, type-checked and linted with everything else. It may use only its parameters and the page's globals, never an import or a constant beside it: pass values as arguments (JSON), page objects with `pageGlobal('tinymce.activeEditor')`, and other page functions by passing them (e.g. `appendButtons`). Type what it touches with a small interface (tinymce/tinymce-api.ts), not `any`. Spec it by running `pageScript(fn, …)` in `vm.runInNewContext` with a stand-in for the page (page-functions.spec.ts): anything it reaches for outside itself fails there as it would in the page.
- **Never reach site globals through `unsafeWindow`** (SKILL.md → "Baseline"). Keep `Postback(...)` as markup that runs in the page's context, e.g. a `href="javascript:Postback(...)"` prop. Don't pass a string to an `on*` prop: Preact makes every `on*` prop a listener.
- **Markup:**
  - Use `class`, not `className`.
  - Props are camelCase, and fallbacks become default values.
  - Reuse the class names in `styles.ts` / `attributes.ts` rather than retyping strings.
  - **Class names are short and readable** (the maintainer's ruling): `ta-x-`, the feature, then the part (`ta-x-image-selector-title`, `ta-x-wishlist-pill-item`, `--ta-x-sticky-toolbar-floating-menu`), never the area, page or tab they sit under, and never generated: live checks, fixtures and bug reports read them. `test/repo/class-names.spec.ts` fails when two `styles.ts` files define one name.
  - **A settings control's id comes from its setting** (`settingId` in `ui/settings`: `game.achievements.individualProgress` is `ta-x-game-achievements-individual-progress`), so `CheckboxSetting`, `SelectSetting` and `ListSetting` take no id. A spec finds one by `settingId(settings.…)` or that id.
  - **A `js-` class only for code that queries it** (the maintainer's ruling): our code's selector (`site-gamer-panel.ts` leaving our settings menu out of the site's gamer panel) or the site's (`InsertAtCursor` finding the emoji picker). Never one as a spec's handle: specs find our elements by their style class, the site's classes and ids, a title, an href (a postback) or their text (`findByText` from `@ta-x-test`). A style key and its `js-` sibling are named alike (`wrench` and `jsWrench`).
  - **SVG attributes are written hyphenated** (`stop-color`, `fill-rule`, `stroke-width`). Preact sets camelCase ones as is on the page, where SVG ignores them (gradients go black, strokes 1px), while rendering to a string converts them, so a `renderElement` spec passes anyway: mount icons in their specs (`mountForTest`).
  - HTML that used to be a string becomes JSX, not `dangerouslySetInnerHTML`; a copy of the site's own element is cloned in (`AchievementLeaderboardLink` clones the bar's child nodes in a layout effect), never set as HTML. The exceptions are build-time markdown and another site's content we show as is (an imported guide), which is cleaned when it's read (`getGuideHtml`).
- **Keyboard and screen readers:** a control that opens or does something is focusable and works with Enter and Space. Use `<button type="button">` where its look can be reset to match (the accordion header, `_accordion.scss`); where the site's CSS styles the element by its tag (`span.button menubutton`, `li` tabs, the hideable row's eye, the wrench's `div.gamer-page`), keep the tag and add `role="button"`, `tabIndex={0}`, `aria-label` and `onKeyDown={clickOnEnterOrSpace}` (`@ta-x-ui`), plus `aria-expanded` when it opens something. An action drawn as a link (`<a href="#">`: Import, Remove, the settings menu's footer links) keeps its `<a>` and adds `role="button"` and `onKeyDown={clickOnEnterOrSpace}`; `linkAction(callback)` (`@ta-x-ui`) is its click when nothing around it should see the click, and `noJump(callback)` when the handlers around it still should (the site's search and filter bar). A callback that reads a ref (`AskForm`'s) keeps its handler written out: lint's `react(refs)` takes the ref read as happening during render. Hidden content that can't be seen is `inert`. Ids that must be unique on the page come from `useUniqueId()` (`@ta-x-ui`): Preact's `useId` starts again in every `mount()` root. Specs press keys with `pressKey(element, key)` from `@ta-x-test`.
- **Hooks:** keep effect dependencies complete, as lint asks (an effect that should stop once it has what it needs returns early instead). DOM writes go in plain functions, since lint flags assigning to hook arguments or refs: a hook argument's DOM property written in an effect goes through one (`setId(element, id)` in `ImprovedImageSelector`, as `react(immutability)` flags `element.id = …` there). Preact 11 exports event handler types from `preact` (`import type { MouseEventHandler } from 'preact'`).

## Checking a component live

On top of [live-site.md](live-site.md) → "Checking a change live", check:
- **Markup and position:** they match the site before the change. Reload 2–3 times, since at `document-start` some insert points race the browser's parsing. A position that varies and also did with the old code isn't a regression, but say so.
- **It sits right next to the site's own controls:** compare `getBoundingClientRect()` top and bottom (and font, padding, line height) with the neighbouring site button or field, not just a screenshot. The maintainer notices a 1px difference.
- **Links with `href="#"` don't jump:** click them for real after scrolling down and check `location.href` and `scrollY` didn't change; handlers call `event.preventDefault()`.
- **Both themes:** switch the site theme yourself (live-site.md → "Switching the site theme") and put the user's back (local.md).
- **When a page behaves differently and specs pass,** compare with a temporary build of the old code (live-site.md → "Comparing with the old code live").
