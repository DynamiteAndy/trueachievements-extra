# Debugging a failing spec

- **To see what a spec is doing, `console.log` it and run that file with `--reporter=verbose`.** The default reporter shows no console output from agent shells, but the verbose reporter does. Prefix your logs so they're easy to grep, and remove them afterwards:

  ```bash
  pnpm vitest run <spec file> --reporter=verbose 2>&1 | grep DBG
  ```

  e.g. `console.log('DBG', document.body.innerHTML.slice(0, 300))` in the test.
- **"Worker exited unexpectedly"** means the wrong Node version (`--no-webstorage` in the Vitest config needs Node 26). Check `node -v`.
- **`[object Object]` rendered as text** means the vnode's component was `undefined`, so an import resolved to the wrong file. Check for a file and folder whose names differ only by case (components.md).
- **`GM_getValue is not defined`**: the Tampermonkey, element, service, storage (settings and IndexedDB), network, page-reset and matcher mocks (`test/mocks/setup.ts`) load through `setupFiles` for the `page` and `repo` projects (`withPage` in `vitest.config.mts`); check the config still has them. In a `pure` spec (lib, site) it means pure code is reaching for Tampermonkey: that code doesn't belong in `pure`.
- **Spies are restored before every test** (`restoreMocks: true`), so don't call `mockRestore()`, and set a spy up in each test (or `beforeEach`) that needs it. Mocks that must last the whole run (`test/mocks/`) can't use `vi.spyOn`, or the restore removes them: use `Object.defineProperty` or `vi.stubGlobal`.
- **Shared state is reset for every test**, so specs don't need their own cleanup for it:
  - **Before every test:** `sessionStorage` is cleared (`test/mocks/setup.ts`); `localStorage`, where the Tampermonkey mock keeps its values, is cleared just before the settings re-read it (`test/mocks/settings.ts`; `test/repo/state-reset.spec.ts` checks it); the page is emptied, and the toast's `toastMessage` and the settings menu's `settingsMenuOpen` signals are put back to null and shut (`test/mocks/page.ts`; a spec doesn't reset them itself).
  - **On every `setHtml`:** it removes all attributes from `<html>` and `<body>` (features add classes there) before loading a fixture.
  - **After every test:** the page services (`mutationObserver`, `resizeObserver`, `intersectionObserver`, `httpIntercept`) are all stopped (`test/mocks/services.ts`). They're page-wide singletons, so without that a listener from one test (e.g. a feature's `listen()`) keeps running in later tests. So no spec stops them in its own `afterEach`, the services' own specs included; they call `stop()` only where it's what the test checks.
  - **`httpIntercept` starts itself when the first listener registers** (there's no `start()` to call), so stub `fetch` **before** the code under test registers its listener, or the interceptor wraps the real one.
  - **Not reset: a listener a spec adds to `document` itself.** `document` lives for the whole file, so add it with an `AbortController` signal and abort it in `afterEach` (otherwise every later test sees it too, e.g. a change-event counter counting three times).
- **`@ta-x-lib`, `@ta-x-fetch` and `@ta-x-page` are spyable in every `page` and `repo` spec** (`vi.mock` with `importActual` in `test/mocks/setup.ts`), so `vi.spyOn(taxPage, 'waitForElement')` just works: don't add the `vi.mock` line to a spec. A spec's own `vi.mock` of one of them wins over the shared one. A spy on a barrel only sees callers that import through it: inside a folder files import each other by relative path, so spy on the file itself there (`import * as stickyHelperModule from './sticky'`; a module's own namespace is spyable without a `vi.mock`).
- **A rejected promise a Vitest mock returns never shows as unhandled:** the mock attaches its own handlers to record how it settled (`mock.settledResults`), so code that drops it (`void forget(url)`) leaves no "Unhandled Rejection" and the run passes. To check a rejection is handled, make it fail below the mock's level, where the code's own promise rejects (GuideSitePanel's forget: `vi.spyOn(IDBObjectStore.prototype, 'delete')` throwing, not `importedGuides.delete` rejecting). `pnpm test:mutate` counts an unhandled error as a catch.
- **A `vi.mock` factory that spreads the real module must await it:** `async () => ({ ...(await vi.importActual('…')), x: vi.fn() })`. Without the `await` it spreads a Promise, which copies nothing, and any other export used then throws `No "X" export is defined on the mock`.
- **Coverage:** `pnpm vitest run --coverage.enabled --coverage.reporter=json-summary --coverage.reportsDirectory=<scratchpad>/cov` (the config already sets the provider and `src`), then read `coverage-summary.json` with a small script. Page functions show as uncovered even when specced, since their specs run them from their source in `vm` (e.g. `text-color-buttons.ts`, `append-buttons.ts`).
- **Don't use `test.concurrent` for tests that touch the DOM or spies.** Concurrent cases share one `document` and one spy, so they overwrite each other's HTML and mocked return values. Keep it for pure functions.
- **happy-dom differs from Chrome** in ways that have bitten specs here:
  - SVG parsed as HTML lowercases `viewBox`, so compare SVGs rendered the same way, not against a string.
  - `el.querySelectorAll('.outer .inner')` finds nothing when `.outer` is an ancestor of `el` (Chrome matches it). Write selectors relative to `el`.
  - `link.href` resolves against `http://localhost:3000` unless `setHtml(path, { url })` sets the page URL; assert `getAttribute('href')`.
  - `style.backgroundPosition` serialises `0` as `0px`.
  - `innerText` is our own stand-in (`test/mocks/element.ts`): spaces collapse, a `<br>` is a line break, blocks start their own line and a paragraph has a blank line around it, as in Chrome. It has no layout, so text Chrome hides (`display: none`) still counts.
  - No `element.ariaLabel` (it's `undefined`; Chrome has it). Match `[aria-label="…"]` instead, which works in both.
  - Scripts don't run (`enableJavaScriptEvaluation: false`): an added `<script>` never executes. Page functions are specced by running their source in `vm` instead (components.md → page functions).
  - Iframes don't load (`contentDocument` is `null`, and a fixture with one logs "Iframe page loading is disabled", which is harmless). Stand in for what a spec needs, e.g. `Object.defineProperty(iframe, 'contentDocument', { value: … })`. **Keep happy-dom's `enableIframePageLoading` off:** turned on, it fetches every fixture iframe's page from the internet and fires their `load` events, which breaks the editor specs.
- **Specs never reach the network** (`test/mocks/network.ts`): a `fetch` that nothing stubbed is refused, and the test that was running when it was made fails, naming the address (a refused fetch alone could pass, since features catch fetch errors). If it names an address you did stub, look for a component left mounted by an earlier test: its effects can run late, during a later test. Return the feature's unmount and call it in `afterEach`, and act only once the component shows the state you mean to act in (don't click an ask form that's still hidden while it loads).
- **Flakes under load:** a time limit a test relies on *not* reaching must have room (`indexed-db.spec.ts`'s "blocked" tests give the service 1000 ms; only the test of the limit itself keeps 100 ms), and a check of something a later re-read updates must wait for it with `vi.waitFor` (the guide-site specs' solutions). A spec that passes alone and fails in a full run is one of these first, not a real catch.
- **The HTML parser closes a `<p>` when a `<div>` opens inside it:** a guide's `<p><div class="lazyYT">` parses back as the div beside an empty `<p>` (the site's own walkthrough markup does the same). Assert on the element itself, not the paragraph's contents.
- **A spec that fails part-way can leave async work running into the next test** in the same file: fix the first failure before reading the second.
