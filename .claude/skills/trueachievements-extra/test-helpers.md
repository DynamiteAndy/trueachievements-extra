# Test helpers and the spec setup

What `@ta-x-test` (`test/index.ts`, re-exporting `test/support/`) and `test/mocks` (the setup Vitest runs for every `page` and `repo` spec) give every spec, each described once here. The recipes that use them are in [writing-specs.md](writing-specs.md); what's reset between tests is listed once, in [testing.md](testing.md) → "Shared state is reset for every test".

## Shared helpers

Use these rather than writing them again in a spec:

- **Page state:** `stillParsing()` fakes a page still loading and returns what finishing the parse does (writing-specs.md → "The page still loading, and yields"). `arriveFrom(referrer, type?)` arrives from a referrer, by `'navigate'` unless told `'reload'`. `recordEvents(type, read, { cancel? })` records each event on the page, read as `read` says, until the test ends.
- **Reading the page:** `ids(element)` gives the children's ids, or their class where they have none. `visibleTabs(root?)` gives the ids of the tab panels shown (`data-tab-visible`). `hiddenThreads()` gives a forum page's thread rows as `'true'` or `'shown'`. The sales folder's own spec helpers: `saleRowStates()` (`news/sales/sale-tables.spec-helpers.ts`, built on `sale-tables.ts`'s `saleRows` selector) gives a sale article's rows as `[href, hidden]`, with `'ad row'` for the site's ad rows; `capturedAdRow()` / `capturedAdSlot()` (`news/sales/ad-row.spec-helpers.ts`) give the site's captured ad row and its `div.dyn-lb` to add to a sale table.
- **Waits:** `outcome(promise)`, on fake timers, says whether a promise has settled and with what. `neverFinds(...selectors)` makes `waitForElement` answer null at once for those selectors only, instead of waiting out its timeout.
- **The page's own fetch:** `stubPageFetch(answer)` replaces it with a `vi.fn` for one test and puts back what it replaced when the test ends; don't save and restore `globalThis.fetch` by hand.
- **Fetched pages:** `fetchDocumentsThroughMemoizeFetch()` routes `memoizeFetchDocument` through a `memoizeFetch` spy (writing-specs.md → "Fetched pages in specs"). `fetchPagesByUrl({ part: html })` answers `memoizeFetch` with the page whose key the URL contains, else `emptyPage`. `emptyMemoizedFetches()` leaves the cache empty and answering at once, for a feature read through `memoizeFetchExtract` with `fetchOk` spied, and returns what puts the real cache back. A spec's own `fetchPages(overrides)` can spread its defaults with what a test swaps out, instead of wrapping the mock.
- **Mounting:** `mountForTest(vnode, parent, before?)` when the spec gives the parent (the site's markup it goes in, or a detached `div` for a component that places itself), mounting like `mount`; `mountInPage(vnode)` when it needs a container of its own on the page, returning `{ container, root }`. Both unmount when the test ends (inside `act()`, so effects' clean-ups run), and `getSettings` and the other settings helpers do too; unmounting by hand first as well is harmless. Anything left mounted keeps its signal subscriptions and listeners into later tests. Never a bare `mount` from `@ta-x-page` in a spec: nothing unmounts it, so its effects and signal subscriptions run on into later tests. Mount inside `act()` when its effects matter.
- **Rendering to a string:** `renderElement(vnode)` renders to static markup: no effects run and clicks do nothing. `renderFragment` gives the whole render, for a component that renders several elements. For a component with state or effects, mount it instead.
- **Fixtures:** `setHtml(path, { url? })` loads one as the page under test (synchronous: don't `await` it). `readFixture(path)` gives its markup as text, for a stub to answer a fetch with or to add to the page; `readFixtureDocument(path)` parses it on its own, off the page, for a page our script reads after fetching it (a guide site's page) or the site's own markup to compare with (Toast's site toast); a fragment fixture ends up in its `<body>`. All take the `@ta-x-test-views/…` path (test/html, one folder per site page: writing-specs.md → "Fixtures: one folder per site page") and read it from the repo, whatever the working folder (test/support/fixtures.ts). Never `fs.readFileSync` in a spec.
- **Elements:** `find(selector, root?)`, `findByText(selector, text, root?)` (an element known only by what it says), `required(value)` and `elementOf(root)` fail the test when there's nothing (writing-specs.md → "Elements a spec needs").
- **Acting as a user:** `click(element)` dispatches a click inside `act()` and returns the event (check `defaultPrevented` on it). It's cancelable and bubbles like a real one. `pressKey(element, key, modifiers?)` does the same for a keydown. `act(() => element.click())`, still in several specs, is fine too where the event isn't needed. `submitAsk(container, value)` types into the ask form inside `container` (an ask loader, a guide site's links) and clicks its button. `openTab()` makes the next `GM_openInTab` return a tab whose `close` is a mock (and whose `onclose` the code may set), to check the tab is closed.
- **Guide sites** (achievement, achievements and DLC pages): `guideSitePanel('xbox-achievements')` (game/extra-guides/guide-site-panel.spec-helpers.ts), by the site's id, finds its panel by its tab panel's id (`guideSiteTabPanel(siteId)`, the selector alone) and gives that site's `panel`, `rows`, `field`, `button`, `submit(url)` and the page's imported `solutions`.
- **The settings menu** builds each tab, and its changelog and documentation views, the first time it shows them open: a spec that reads every panel calls `showEveryTab(menu)` (all-pages/settings-menu/settings-menu.spec-helpers.ts) first, which opens the menu, shows each in turn and goes back to the first tab. A static `renderElement` of the menu has no panels' contents.
- **Fake timers:** `useFakeTimers(options?)` and `tick()` (writing-specs.md → "Waiting in specs").
- **The resize observer:** happy-dom lays nothing out, so `stubResizeObserver()` stands in for it and returns `{ observe, resize(element), follows(element), followedSizes() }`.
- **Settings:** `setSettings({ 'path': value })` sets settings (switching parents on first). `getSettings(<Panel />)` returns `[id, setting path]` for each shown row of a settings panel, found by changing the control and seeing which setting changed (then putting it back); `shownSettings` gives just the ids; `getAccordions(<Panel />)` gives the accordions' titles (each checked to have its content after it). `changeSetting(control, value)` changes a checkbox or select as a user does, inside `act`. Rows hidden by a setting aren't in the page, so check both states. `changeSettingLive`, `expectAppliesLive` and `withoutUniqueIds` are for settings that apply live (writing-specs.md → "Settings that apply live").
- **Entry specs:** `describeEntry(…)` (writing-specs.md → "Entry specs"). **Parsing:** `stillParsing()` and `withoutBody()` (writing-specs.md → "The page still loading, and yields" and "Starting before the page has a body").

## The Tampermonkey and settings mocks

- **Settings are signals:** `storage/settings-tree.ts` holds every setting as a persisted signal that reads Tampermonkey storage once. Before each test `reloadSettings()` re-reads them (test/mocks/settings.ts calls it); `GM_setValue` and `GM_deleteValue` in a spec reach them through the mock's change listeners, as in Tampermonkey: a delete of a key with a value tells its listeners, with `undefined` as the new value (`test/mocks/tampermonkey.spec.ts`). **Never `vi.unstubAllGlobals()`**: it removes the Tampermonkey stubs too and the next test's reload fails with `GM_getValue is not defined`; put back only what you replaced (e.g. `globalThis.fetch`). The mock stores values as Tampermonkey does (checked live): a copy, so an object read back or handed to a listener is never the one written, and `undefined` kept as a value (listed, and read back as `undefined` rather than the default).

## Leaving nothing behind

- **A feature that mounts something returns its unmount** (`walkthroughPage`, `manageWalkthrough`, `populateAsideContent`, `improveImageSelector`, the toast). Its spec registers that with `onTestFinished`, and only when it's a function: `onTestFinished(undefined)` fails the test when it ends.
- **Clean-up goes in `afterEach` or `onTestFinished`, never at the end of a test body**, which a failed assertion skips. The shared helpers do theirs (fake timers, mounts, `recordEvents`); a spec's own covers a global deleted, a listener removed (an `AbortController` signal) and an IndexedDB connection closed (indexed-db.spec's `holdOpen` closes its own when the test ends).
- **`setHtml` always sets the address**, to `http://localhost:3000/` (where happy-dom starts) unless given a `url`. state-reset.spec pins this.

## Exact-check matchers

[test/mocks/matchers.ts](../../../test/mocks/matchers.ts), loaded for every `page` and `repo` spec: `expect(element).toHaveExactClasses(['a', 'b'])` (these classes in any order, and no others; a class listed twice fails, so a typo'd duplicate can't hide) instead of `classList.contains(x)).toBe(true)` (which pins one class and misses others coming or going), and `expect(element).toBeLastChildOf(parent)` for where something was added. It also adds an equality tester: DOM nodes are equal only when they're the same node, in `toEqual` and the call matchers too (writing-specs.md). Their types extend Vitest 5's `Matchers<R, T>` (its type parameters exactly as declared, or the merge fails).

## Lint rules for specs

`.oxlintrc.json`: everywhere, no `any` and no `@ts-ignore` (`typescript/no-explicit-any`, `typescript/ban-ts-comment`), and the ARIA checks listed one by one (`jsx-a11y/…`: misspelt or unsupported ARIA, a role missing what it needs, no positive `tabindex`); the plugin's rules that flag the components.md patterns (`<a href="#">` actions with `role="button"`, the site's own cells and labels) are listed as `off`, as the plugin turns some on by default. A plugin added to the top `plugins` goes in the spec override's `plugins` too: with `jsx-a11y` at the top only, lint gained vitest warnings across the specs. The spec override, whose `files` include `src/**/*.spec-helpers.ts` so spec helpers follow it too, adds: no `.only` (`vitest/no-focused-tests`, caught by lint in the pre-commit hook, and by Vitest's `allowOnly` on CI), no `expect` inside an `if` (`no-conditional-expect`), no two tests with one title, every test asserts (`expect-expect`: a helper counts if its name starts with `expect` or `assert`, or is `describeEntry`, so name a checking helper `expectX`), `toBeNull()`/`toBe(true)` over `toBe(null)`, no `expect` outside a test. `vitest/valid-expect` is turned off in the override (it rejects Vitest's `expect(value, message)`). [test/repo/spec-style.spec.ts](../../../test/repo/spec-style.spec.ts) fails on what lint can't see: an optional chain or `?? []` inside `expect()` under a matcher that also passes when the thing is missing (`.not.`, `toBeFalsy`, `toEqual([])`, `toHaveLength(0)`…), and `.not.toBeNull()`, `.toBeTruthy()` or `.toBeDefined()` on `find()`/`required()` (they throw first). Use `find` or `required`, then an exact matcher.

## Isolation and the three projects

- **Spec files share a worker's page** (`isolate: false`, the maintainer's choice, for speed). Each file still starts with fresh modules ([test/mocks/fresh-modules.ts](../../../test/mocks/fresh-modules.ts), `vi.resetModules()` before setup.ts), and the shared state is reset for every test (testing.md has the list). Run a few shuffled runs (`--sequence.shuffle --sequence.seed=<n>`) after adding something page-wide (a global, a listener on `window`), as what a file leaves on the shared page can reach the next one.
- **Three projects** ([vitest.config.mts](../../../vitest.config.mts)): `pure` runs `lib` and `site` specs in plain Node with no setup (`./src/lib/*.spec.ts` and `./src/site/!(cookies|achievement-status|postback).spec.ts`: `cookies.spec`, `achievement-status.spec` and `postback.spec` need the page; pure specs take their timers from `@ta-x-test-timers`), so pure code reaching for `document` or `GM_*` fails there; `page` is everything else under the page and Tampermonkey mocks; `repo` is `test/repo`. A project with `extends: true` merges list settings (`setupFiles`) with the root's rather than replacing them, so the page setup is set only in the projects that use it. The "Failed to load iframe page about:blank" lines in a run are happy-dom's, and harmless.

## `unstubEnvs`

**`unstubEnvs` is on in the config, `unstubGlobals` isn't** (the maintainer's choice): an env a test stubs (`vi.stubEnv('NODE_ENV', 'development')`) is put back after it, so a spec needn't undo it. Globals aren't: the Tampermonkey mock (`test/mocks/tampermonkey.ts`, loaded by setup.ts) stubs the GM_ APIs once, and unstubbing them after each test would undo that. [test/repo/env-stubs.spec.ts](../../../test/repo/env-stubs.spec.ts) pins both (it fails with `unstubEnvs` off).
