# Site quirks found so far

Check these before restyling or adding controls; each was found live, not by a spec.

## Themes, CSS and the site's look

- **Themes:** the site sets `data-theme="normal"` or `"dark"` on `div.page` (not the body; its `g-li` class is on both; `""` for light straight after a live toggle, until a reload). Check both: switch it yourself (live-site.md → "Switching the site theme"). Put dark overrides in a `[data-theme='dark'] { … }` block inside the `body.trueachievement-extras` block; a nested `[data-theme='dark'] &` compiles to `[data-theme=dark] body…`, which never matches.
- **`input.button:hover`** drops the bottom border with `!important`, pressing the button 2px and shrinking what's around it. Our ask buttons keep it with `!important`, in the resting colour of each theme (black on the light theme's blue button, `rgb(85, 85, 85)` on the dark theme's grey one).
- **`input[type=text]`** is capped at `max-width: 250px`; game pages don't load the site's border-box textbox style (fields are `content-box` there), so a 100% field needs `box-sizing: border-box`.
- **Buttons:** `.button` is styled for links (`a.button`, flat blue); `input.button` gets the grey raised look, which the maintainer chose for our forms.
- **Icons are our own, never the site's Font Awesome:** the site has an FA4 subset (`<i class="fa fa-…">`, no `fa-plus`), but our markup uses the SVG components in `src/ui/icons` (Font Awesome 7 free solid/regular, drawn by `FontAwesomeIcon`; add one per icon). Size an icon replacing a site glyph with `height` in `em` (about `0.86em` matches an FA4 glyph at the same font size; the close × needs `1em`) and `width: auto`; set a colour the site gave only via an `fa-*` class (e.g. `fa-close` is `#e53e3e`).
- **Font Awesome 7's outline icons look thinner than the site's FA4 glyphs** at the same size (the emoji button's smiley). Thicken one with a stroke on its path (`stroke: currentColor; stroke-width: 16`, in the icon's 512-unit viewBox), and compare live beside a temporary `<i class="fa fa-…">` in the same colour and size before picking.
- **A media query's width counts the vertical scrollbar; the page's width doesn't.** The site's `.middle` is a fixed 1,200px, so in a window 1,200 to about 1,215px wide it overflows by the scrollbar's width and the page scrolls sideways. `base.scss`'s `.middle { width: 100% }` below 1,350px prevents that (history.md has how that was found). Before calling a width rule dead, check a window just above each breakpoint, by less than a scrollbar (e.g. 1,200 to 1,215px), and compare `document.documentElement.scrollWidth` with `clientWidth`.
- **The page's columns:** `1rem` is 10px (`html` is `font-size: 10px`). `.page > .main` is a grid at most 1,200px wide; `main` beside an aside is capped at 870px (`.page > .main > main`), and the site's `no-aside` class on `main` lifts the cap (the staff manage, walkthrough and edit pages have it). Below a 900px window the aside drops under `main` but the 870px cap stays, so from about 886 to 899px (a 15px scrollbar) `main` stops short of the right edge, on the site's own walkthrough pages too.
- **Side lists** (First Winners and the like): rows are `5px 0` padding, 18px line height and a 1px line under every row, `#eee` (`#222` on the dark theme); the site leaves a list's last row without a line, and another of its rules trims an `li`'s top padding to 2px. These rules hit **any** `ul li` in a side section (`aside > section:not(.ns) ul li`, `aside ul li`), including ours that aren't lists, such as tabs, and their line colour beats a `border-bottom` shorthand of lower specificity: reset them in the component's scope. Side sections end 14px below their last line of text, 8px below a list's last line. On the dark theme the side-list rule (`.page[data-theme="dark"] aside > section:not(.ns) ul li`) also sets every line's colour to #222, so a clear or coloured `border-top` on an `li` needs setting again in our dark block.
- **Side section children:** `aside > section:not(.ns) > div` (and `> h2`) is styled as the section title (1.4rem and so on), so put a section's body in an `article`, never in direct `div`s. The site's `ns` class turns off the whole side-section look (background, 8px 10px padding, 12px text, side-list rows); its Popular Content box uses it and styles itself.
- **A `<label>` takes no ARIA role** (Preact's types refuse `role` on it): the settings menu's close keeps `label.close` for the site's `.labels label` look and puts a `span role="button"` inside it.
- **The browser's default focus ring is dark** (`rgb(16, 16, 16) auto` in Chrome), so it barely shows on the dark theme's header (the wrench). It appears only for keyboard focus (`:focus-visible`), never for a mouse click.
- **Flex rows** won't shrink below their content without `min-width: 0`; use a grid (`minmax(0, 1fr) auto`) when a long value shares a row with fixed controls.
- **Copying site CSS into our stylesheet:** keep the site's specificity. Nested inside our `body.trueachievement-extras` block, the copies outranked our own styles (the settings menu's tabs went empty, as the site's `.contents > div { display: none }` beat our tab rule). Put them at the top level with our class inside `:where()`, which adds no weight.
- **Sass variables in CSS custom properties** (our own SCSS): Sass leaves a custom property's value as text, so `--x: $y;` compiles to the literal `$y`. Interpolate it, `--x: #{$y};`. And give lengths a unit even when zero: `calc(-1 * 0)` is a number, which `translateY` rejects, where `calc(-1 * 0px)` works. Check with `sass.compile` or the page's stylesheet.
- **Keyboard focus:** the site shows none on its links. Its own stylesheet (the large inline one in the head) has `a, a:active, .pointer { outline: 0 !important; }`, and it has no `:focus` styles of its own. Elements that aren't links (our `li role="tab"`s) get the browser's default ring, which is near-black and barely shows on the site's dark bars. So a focus style of ours copies the site's hover look where it has one, with a ring added for the keyboard only (`:focus-visible`). Shopping extensions inject `content-*.css` sheets with their own `:focus-visible` rules: they aren't the site's.
- **News article tables in the dark theme:** the site's dark rule sets the cells' `border-color` more specifically than ours can be nested, so a border colour of ours on a sale table's cells needs `!important`. Removing a cell's side border (width 0) rather than colouring it changes the table's column widths by half a pixel: make it transparent instead.
- **The homepage's `.middle` is 1200px wide** at a 1504px window: the site caps it there itself.

## Signed in or out, and the gamer's settings

- **Signed out:** the header has a login box (`div.login-full`) where the gamer toggle (`[data-tgl="nav-gamer"]`) is, and there's no gamer panel (`.nav-gamer`). The site also doesn't load the gamer panel's styles then (only `.nav-gamer { display: none }`) or its `fade-content` keyframes, so the settings menu, which borrows that look, carries copies of them. `GamerID` is the cookie the site's own scripts check for a signed-in gamer; signed out it's missing.
- **Every page is sent with the signed-out header:** `header nav` has the login box (`div.login-full`) even for a signed-in gamer, and the site's script swaps in the gamer toggle (`div.gamer[data-tgl="nav-gamer"]`) and the gamer page link (`a.gamer-page`) later. So don't decide signed in or out from which of the two is found first (waiting for either found the login box while parsing, and the wrench ended up before the toggle with the menu at the end of the page): use the `GamerID` cookie, as the site's own scripts do, then wait for the one that will be there. A plain `fetch` of a page gets the same signed-out header. Check positions live with booleans (`toggle.nextElementSibling === wrench`): the privacy filter blocks the header's class names and attributes as a JWT.
- **The gamer's own site settings change the markup** (`/customize.aspx`): e.g. grouping DLC in achievement lists, sorting by won first, showing secret achievements, hiding solutions by default, hiding completed games, the forums' unread-only and show-all defaults, hiding sponsored news, and Pro's "Show ads". So a page can differ between accounts: local.md records the user's, and when a feature reads markup one of these changes, check it with the setting both ways (put it back after, as with the theme) or say which way it was checked ("Show secret achievements I don't have" saves as soon as it's switched; the others weren't tried).

## Page loading and parsing

- **`document-start`:** some insert points race the browser's parsing. **A long page is still parsing when the features start** (Halo MCC's achievements had 271, then 351, of its 700 items while `readyState` was `loading`; a 34-item page was complete), so code that reads a whole list must wait for `readyState !== 'loading'` (or `DOMContentLoaded`) first, and specs can't show it (fixtures are complete). Check list-reading features on a long page; and a page parsed with `DOMParser` resolves `.href` against TrueAchievements, so read `getAttribute('href')`.
- **Chrome parses a short achievement list in one go.** On 50 and 164 item lists, a mutation observer only ran once the page was parsed (`readyState` already `interactive`, every item there), so "as soon as an item is parsed" means the end of the parse there; long lists pause mid-list (above). With the site's "Sort by won first" game option on (`chkSortByWonFirst`; local.md says whether the user has it on), the items not won come last.
- **A news article's quick reply box is added after the page is parsed** (seen on the Black Friday sale article): a query at `DOMContentLoaded` finds no reply box, and the site's script adds it about half a second later, so emojis' listener is what picks it up.
- **A walkthrough thread's "published" post separates its lines with `<br>`:** its `textContent` reads "…published.You can find it here…" (no newline), and its `innerText` "…published.\n\nYou can find…".

## Forms, filters and post backs

- **Filters are ASP.NET post backs:** a game's achievements / challenges / DLC status radios, its clips dropdowns and manage walkthrough's status filter all call `Postback('<control>', '<arg>')`, which submits the page's whole `#frm` form (so one post carries every field). The server ignores the filter in the URL and doesn't remember it between page loads. Exceptions with a plain URL: a game forum's tab (`?type=all|community|gameinfo`) and manage walkthrough's selected walkthrough (`?walkthroughid=<id>`, though that resets the status filter).
- **The site colours a plain button's text grey (`#bbb`) and wins over ours:** a bare `<input type="submit">` or link we style as a button needs `color: #fff !important` (the settings menu's footer buttons and its lists' Add Keyword).
- **The site's page form (`#frm`) wraps everything, our controls included:** its first submit button is our settings menu's Add Keyword (the menu is mounted in the header), so Enter in any text field of ours clicks that button, not the field's own Save. Handle Enter in our forms ourselves.
- **The achievements page's filter panel moves to `?filter=1`:** its Apply (`#btnApply`: the DLC view All / Owned / None, the achievement flags, the list order) posts back to `/achievements?filter=1`, not the page's own address, and lists only what passes. A plain GET of `/achievements` still lists every achievement, so a copy cached by its address is never a filtered one (the refresh of a visited page looks its address up exactly). Only the status radios post back to the same address.
- **A page can tell the user's own change from a fresh visit by its referrer.** A filter post back is a `POST` to the same address (the page itself can't see the method: the navigation entry says `navigate` either way), and the games forum's thread tabs are plain `GET`s of `?type=…`. Both arrive with `document.referrer` at the page's own pathname, while a fresh visit's referrer is another page, or empty. Defaults that must only apply on arrival (default status, default thread) can rely on that instead of a stored marker.
- **A filter post back sent before the page finishes parsing works** (for clicking the default status early). The achievement filters' `Postback()` is an inline script near the top, the status radios sit just above the list, and `__VIEWSTATE` is at the top of the form. Removing every form field after the list (the DLC rating dropdowns, `__VIEWSTATEGENERATOR`, the gamer nav checkboxes) and then clicking a status radio still posted back with no error, and the filter applied. On Digimon Survive, a post back without its rated DLC's dropdown kept the rating (a fresh GET still shows it). The gamer nav settings (dark theme, sticky header, emojis, game properties) are added after load, not in the server HTML, so the filter post never handles them. A page rendered by any post back shows the rating dropdowns unset, even when they were sent: a fresh GET is what shows the stored rating.
- **A solution's "Add comment" link submits the comment form** (`href="#"`, but it posts, empty or not: an empty one came back "The Comment must be specifed"). It doesn't just open the box: never click it for a check. Open the sub-comment editor's emoji picker by its smiley button in an editor that's already showing.
- **Option without a value:** the clips dropdowns' "Anyone" is `<option>Anyone</option>`, so its value is its text ("Anyone"), not `''`. Compare against the site's real option values.

## Sticky header and scrolling

- **Sticky elements and the sticky header:** our sticky header hides scrolling down and slides back (79px) scrolling up. Anything we stick (`applyStickyElementStyle`) must clear it while it shows, including while its container's top is still inside the header's 79px. The site itself toggles TinyMCE's toolbar between `static` and inline `position: fixed` at the window's top, so our `top` only applies once fixed. When ours sticks, and why: staff-pages.md → "Edit walkthrough sticky toolbar". CSS `position: sticky` doesn't work there: `main` is `overflow: auto`. To check, scroll down past the element, then back up in small steps (as a wheel does) and compare its top with the header's bottom.
  - **The header grows after load** (50px at `document-start`, 79px once the site fills it in), so anything sized from it follows it (`resizeObserver`), never a value read once.
  - **The browser scrolls on its own:** putting a reloaded page back where it was, and keeping what's in view in place as the page above it changes size (the edit page shrank 39px as it loaded). Those are ordinary `scroll` events, so scroll-driven code that should only react to the user checks for user input (`USER_SCROLL_MS` in `StickyHeader`).
- **The header's menus (Gaming, Community, My Links) open on hover, not by a class:** each is `.nav-primary .items > li > div`, shown by the site's `li:not(.search):hover > div` rule (desktop, 768px and wider), absolute at `top: 100%` of its `li` (which is `position: relative`), 300px wide. Their `open` class is on all of them all the time, so it says nothing; `li.matches(':hover')` does. My Links is about 670px tall, so in a short window its last groups are below the window while the header is fixed. Below 768px the site shows the list through `.items.open` instead. A menu is `display: none` until hovered, with no transition, and already shown when its `li`'s `pointerenter` fires (`:hover` applies first), so it can be measured then. The site's root font size is 10px, so `1rem` is 10px. On desktop their links have `padding: 4px 8px !important` (two to a row, half the menu each), and every div in a shown menu is made a flex row (`li:not(.search):hover div > div { display: flex !important }`), so a box of ours inside one needs its own `display` with `!important`. The longest links (Gaming's "Game Pass …") already wrap in the site's own 300px menu.
- **The site's gamer panel (`.nav-gamer`) is added once and kept** for the page's life (checked through load, opening and closing it, idle time and a theme change): only its `open` class changes, so watching that element's `class` is enough.
- **The site's sticky TinyMCE toolbar, and the header's heights.** The site's `StickyToolbar()` (external script) measures the toolbar's page offset once at load and on every jQuery window scroll sets it inline to `position: fixed; top: 0` once `scrollTop()` passes that offset (until the editor's last 80px), else `static`: so anything moving the editor afterwards leaves it stuck too early or too late. Ours overrides that (staff-pages.md → "Edit walkthrough sticky toolbar"). The site's `<header>` is 79px tall in a wide window and 69px in a narrow one (40px bar + 29px promo bar), 50px wide without the promo bar; the promo bar's ✖ dismisses it for the account, so hide it with a temporary style for a check. When the header changes height, the sticky header's spacer (`HeaderSpacer`) moves the page by the same amount a moment later, so anything placed against the page re-measures a frame after. Before the user's first scroll, the header has neither `y-show` nor `y-hide` and is in view. The edit page's wheel scrolls go to the editor's iframe when the pointer is over it: scroll with the pointer at the page's edge.
- **The walkthrough page's page history (`#chWalkthroughPageVersions`):** a 270px column (`flex: 0 1 auto`) beside the preview (`flex: 1`), with a `0 10px 10px 0` margin (the gap to the preview), and `height: 100%`: 492px in place, 6383px at `height: auto` (its list), and the window's height once `position: fixed`. Anything that takes it out of the flow must hold its place with its width, flex and margins, and keep its height.
- **Chrome's scroll anchoring and anything we fix or unfix:** making an in-flow element `position: fixed` takes it out of the page's flow; if that moves the content Chrome has anchored to, Chrome shifts the scroll position to compensate, which fires another scroll. Hold the element's place in the same change (padding or a spacer), and read its size before switching the class: a forced layout in between (e.g. reading `offsetHeight` after) is anchored to as well. To confirm anchoring is the cause, try `html, body, main { overflow-anchor: none }` temporarily.
- **Fixed elements trail the page by a frame:** Chrome scrolls on its own thread, a frame ahead of scroll handlers, so an element fixed to the window and moved to follow the page on each scroll trails it (seen in a screen recording, not in a script's measurements). Anything that must move with the page should be positioned in it (absolute or sticky), not fixed and moved.
- **Transform animations run on that thread too** (the header slide), so an element correcting for one from a script each frame trails it; take the animation off the element instead.
- **Moving in step with the header's slide:** copy the slide itself rather than giving the element a transition of its own. `header.getAnimations()` has it as a `CSSTransition` (`transitionProperty: 'transform'`, keyframes `translateY(0px)` → `translateY(-100%)`, 0.5s `ease`; turned round mid-way, a new one from part-way with a shortened duration), and `element.animate(keyframes, timing)` with `startTime` set to the header's runs both as one. A transition just begun has `startTime: null` until its first frame; setting a copy's start time to null stops it where it is, so wait for `ready`.

## Game, achievement, news and sale pages

- **Achievement pages:** the site puts its solutions (`h2#oSolutions.block.topmargin` + `ul.posts`) straight after `#divDynLb`. There's no video player (`.nn_player_w`) any more in the server's HTML; older captures (`test/html/achievement-page/old-video-player.html`) still have one, and the page's inline ad script can still build it. An achievement with no solutions has no heading or list at all (an `.add-comment` box instead), so anything that adds solutions builds them (`SolutionsList`). Heavy Fire: Shattered Spear (`/game/Heavy-Fire`) has many achievements without solutions, for checking that (with a guide site linked: local.md may name a game the user has linked).
- **A game's challenges list has a heading row** (on Gears of War 4): `.ach-panels` holds `<li class="heading">Expired Challenges</li>` between the current and expired challenges, among the `li.w` (won) and `li.nw` (not won) items, and it stays in the Won and Not Won lists. Anything counting or finding list items must skip `.heading`. The achievements list has none.
- **`DropdownButtonPanel_Toggle`** (the site's emoji/smiley panel toggle) is defined by the site's bundle on forum threads and news articles, but not on achievement pages, whose reply box needs our copy. Our sandbox can't see the page's functions, so the page script checks for it itself (`defineDropdownToggle`).
- **Reply box toolbars style their buttons by depth:** `.adv_editbox .formatbuttons > div > a` (and `> span`) gives a toolbar button its padding (`7px 12px`), size and grey colour, so a control of ours must be a slot itself (a `div` directly in `.formatbuttons`) to look like the site's; one level deeper it's a blue link. The smiley and controller buttons are each such a slot (a trigger and usually its `.dropdownbuttonpanel`); on a forum quick reply their group sits at the toolbar's top right. Every `.dropdownbuttonpanel` in the box is `right: 0` and `max-width: 290px` (`!important`), and `DropdownButtonPanel_Toggle(this)` opens the first `div` in the trigger's parent.
- **The site's toasts don't stack, and use our toast box** (checked on Gears of War 4's achievements and `/win-xbox-games`): the site's `$.toast({ heading, style })` is the jQuery toast plugin with `stack: 5` in its defaults, but before adding a toast it removes every `.jq-toast-single` jQuery calls `:hidden`, and jQuery says a showing toast is (display block, opacity 1, still `:hidden`). So each toast replaces the last, even a second apart: three in a row leave only the third. Our Toast replacing its own message matches. The plugin puts its toasts into the first `.jq-toast-wrap` on the page, which is ours (`ta-x-toast`, mounted on every page), so the site never makes its own: a site toast while ours shows sits beside ours in our box (both shown, no errors, each hiding on its own timer). A hidden site toast stays in the box with the site's `displaynone` class until its next toast clears it.
- **The giveaway (`/win-xbox-games`):** a new game each day. Signed out, an entry post is answered 200 with "Please register or log in to enter this competition" and the entry link still there. Once entered, the page has no countdown (it's only shown next to the entry link).
- **Sale tables sort with the stupid-table jQuery plugin, bound late.** The site calls `$("table.interactive").stupidtable()` from `head.ready` (its script loader), so a header click before that does nothing. A click goes unsorted → asc → desc → asc, and the plugin sorts in a short `setTimeout` before setting `sorting-asc`/`sorting-desc` (14 to 52 ms in a tab in front). `$(th).stupidsort('asc' | 'desc')` sets an order outright, and the site's region code calls it that way on headers that already have a `sorting-` class. Reach it from a page function (`createPageScript`), never `unsafeWindow`. A price cell holds every region's price; `innerText` gives the one shown. When searching the site's scripts for jQuery plugins, test for `.fn.` with `includes`: a regex built inside a template string loses its backslashes.
- **A sale article's layout** (40 articles): `section.sale` holds `div.region-selector`, then per platform an `h2`, and per table an `h3` and a `div.tab-w` holding the `table.sale`; a platform's later tables have their `h3` alone, straight after the previous table. The site adds in-content ads (`div.dyn-lb` > `#in-content_N`) after load, anywhere among them, even signed in; the server HTML has none. To list sale articles, read `/news/type/Sale` (`?page=2`…).
- **Ad rows in sale tables are added after load:** `<tr><td colspan="100"><div class="dyn-lb"><div id="in-content_N">…` rows, the first after the 4th game row and then about every 10, inserted by the site's scripts. They're never in the server HTML (a fetch of the page has none). TA Pro accounts don't get adverts ("No adverts on the TrueAchievements website", `/gopro`), but the empty ad elements are sometimes left behind, rows the site's table sort then gathers at the top as empty strips (Hide Ad Rows hides those). To check code that walks the rows with the adverts in place, use the signed-out test browser (live-site.md → "Opening a page"; the built-in browser has no Tampermonkey, so our code doesn't run there), or with TA Pro switch on "Show ads" for the check (no need to ask, as with any site setting: SKILL.md → "Rules"; `/customize.aspx`, `#optShowAds`, in a hidden tab: click the input; it saves at once), then switch it back and confirm after a reload (local.md: whether this account has Pro). Code that walks a sale table's rows must expect a row with no link (`sale-article/owned-picks-with-ad-row.html` has one).
- **A sale row's edition or bundle links only its base game's page:** "Monster Hunter Stories 3 Deluxe Edition" on a sale's bundles article links `/game/MONSTER-HUNTER-STORIES-3-TWISTED-REFLECTION/achievements`, as the game's own row does, and an Expansion Pass row links each DLC it holds. So a game or DLC link can't tell a product from what contains it. Each row's buy link can: `/ext?u=<xbox.com store address>&s=…`, the address ending in the product's 12-character store id, which is the same in every region and on the wishlist. A few add a SKU after the id (`/9N5DLKQ7W3QX/0010`: 11 of the Black Friday sale's 2,905 buy links, in-game currency), so take the last part shaped like an id, not the last part. Its name part isn't (`Age-of-Mythology-Retold--Obsidian-Mirror` on the article, `age-of-mythology-retold--obsidian-mirror` on the wishlist), so compare only the id. One product can have two rows in an article (DEATHLOOP's Deluxe Pack in the Black Friday DLC article).
- **A wishlist (`/gamer/<name>/wishlist`, public, server-rendered) lists each item's sale listings, including the products that contain it:** `?sale=1` keeps what's on sale. An item with several listings has them in `.wl-strip details.wl-listings .wl-row`: title link `/products/<id>/…`, a `.wl-pill` (`game`, `bundle`, or `addon` for DLC and passes), a note in `.wl-title small` ("Single game", "DLC only", or "2 DLC, 1 on your wishlist" for a product containing it), buy link in `.wl-cost a`. An item on sale as itself alone has a single buy link in `.wl-head .wl-price a` instead. An edition of a wishlisted game is a `bundle` that says "Single game". Only DLC with a TrueAchievements DLC page can be wishlisted (its page's `…` menu); a product page's own heart (`#add-wishlist`) is hidden. A DLC item shows a `span.wl-badge` "DLC". The `Games`/`DLC` pills filter by `?show=`. Each item's remove link is a postback that saves (`javascript:Postback('btnRemoveFromWishList', <id>)`): never click it.
- **Sale tables squeeze their narrow columns:** `td:nth-child(n+2)` asks for 62px, but in a 780px table the info column gets about 47px, and the table ignores an inline SVG's width when sizing it (an SVG sized only by its height has no min-content width), so our eye overflowed the cell. Give a wrapper an explicit `min-width` to make the column grow. Test layout changes live by injecting a `<style>` first; a big sale (Black Friday, 3,000+ deals) shows the cases.
- **A DLC's page has two pages below it:** `/game/<game>/dlc/<dlc>/difficulty` and `/completiontime` (its difficulty and completion time votes). A check for "a DLC page" has to rule those out (`^/game/.*/dlc/(?!.*/).*$`).
- **Achievement list group headers:**
  - **A game without DLC** has one header, `.pnl-hd.game[data-gid]` (Celeste, Inside, Limbo).
  - **With DLC grouped** (the gamer's "Group DLC in achievement list"; local.md), the base game gets `.pnl-hd.game` with no `data-gid`, and each DLC `.pnl-hd.game.dlc` (Age of Mythology: Retold).

## TinyMCE (the edit walkthrough page)

- **A colour button's panel is a popover, not a menu:** `body > .mce-floatpanel.mce-popover`, with an arrow (`.mce-arrow`), a 10px gap for it, and the panels' fill (`#404952` in the dark skin, where menus are `#2f3740`). The sticky toolbar's rule for where floating menus open only matches `.mce-menu`. `panel: { classes: 'menu' }` in the button's settings makes it one (TinyMCE adds `mce-` in front); add classes that way, as TinyMCE writes a panel's classes again when it places it. The arrow and gap stay, so hide them. The panel is made on the button's first open and hidden and shown after (`style.display`), and is sized when made: content added later needs its `width`/`height` overridden.
- **jscolor inside a TinyMCE panel:** with `container` set, it draws in the container's flow (not at the page's body), so a click in it is the panel's and the panel stays open. A swatch can only be a colour (with its opacity slider off, a clear one picks opaque black), so a control of our own among them is caught on the document's capture phase before jscolor's click on the swatch. jscolor redraws its swatches on every `show()`.

- **The site adds some TinyMCE buttons itself:** on a walkthrough's edit page (seen on one in local.md) its toolbar already has Controller Buttons and Insert Xbox captures, each in its own group (not ours). Our scripts for them skip when they're there (`injectTinyMCEScript`'s `siteButton` option). Captured in `test/html/staff-edit-walkthrough-page/tinymce-site-buttons.html`.
- **TinyMCE's floating menus** (the edit walkthrough): each menu is created on its button's first press, added to `<body>` as `div.mce-container.mce-panel.mce-floatpanel.mce-menu`, and reused on every later open (a `data-` attribute on it stays; TinyMCE doesn't rewrite it). A closed one stays there with an inline `display: none`, which is how to tell whether one is open. A menu opened inside a dialog (e.g. Table properties' Alignment) also has `mce-fixed`; the toolbar's never do, stuck or not, so `:not(.mce-fixed)` tells them apart. Submenus have `mce-menu-sub`. Menus (Paragraph, Table…) are placed when they open, and our sticky toolbar moves them under itself; anything placed before the page above the editor has settled ends up wrong (725px low), so they're placed again as a toolbar button is pressed. Hover submenus (e.g. Table → Insert table) open beside their item: leave them where TinyMCE puts them. A dialog's menu opens upwards when there isn't room below (TinyMCE's own), and opening a dialog scrolls the page so the dialog is in view, which unsticks the toolbar. There's no menubar and no context menu plugin (plugins: lists, link, image, print, searchreplace, wordcount, visualchars, fullscreen, nonbreaking, save, table, directionality, paste, textpattern, anchor).
- **A format menu's previews keep the theme they were built in:** TinyMCE styles Paragraph's options (Heading 1 and the like) once, from the editor's content, when the menu first opens, and only the dark theme gives them colours (`#bbb` on a `#444` box). `syncThemes` clears those two on a theme change, so a menu opened before it takes the menu's colours. **The site's skin has no Select all icon:** its `skins/light/skin.min.css` has no `.mce-i-selectall` rule and its `tinymce` font has no glyph for it (`\e000`–`\e035` are other icons, from `\e036` on empty), so the button is blank in either theme. **An svg drawn into a TinyMCE button doesn't take the icon colour:** the skin's reset gives everything in a button `color: #333` (`.mce-widget *`), the svg and its path included, so a `currentColor` icon draws near-black on the dark skin; give both `color: inherit`. The dark skin edges its glyphs with `text-shadow: 1px 1px #000`, which an svg takes as `filter: drop-shadow(…)`.
- **TinyMCE dialog dropdowns are floating menus too:** a dialog's listbox (Table properties → Alignment) opens as `body > .mce-menu.mce-floatpanel`, like the toolbar's menus, so a rule written for the toolbar's menus catches them (our sticky toolbar rule moved one 533px below its field). Tell them apart by what opened them.
- **TinyMCE dialogs** are absolutely positioned with an inline style on every part, and their inputs are TinyMCE widgets: the Table properties dialog's colour fields are `.mce-colorbox input` under labels "Border color" / "Background color" (`staff-edit-walkthrough-page/tinymce-table-properties.html`).
- **TinyMCE's light skin and the editor's own theme.** The site's `skin.min.css` (TinyMCE's lightgray) gives toolbar buttons no border (`.mce-toolbar .mce-btn { border: 0 }`, and `border: 0 !important` on a group's first and last), 3px top and bottom padding, and dropdowns 20px on the right; its panels' border is white, the same as their background. TinyMCE sets the editor's border width inline (`style="border-width: 1px"` on `.mce-tinymce`), so only `!important` removes it. Each toolbar row puts its buttons 2px below its top and none above its bottom; each toolbar group has `margin: 2px 0 0 2px` and each button `margin-left: 2px`. Our dark skin gave its buttons a border and 4px, so the two themes' toolbars differed in size; the toolbar's box is now set for both in `charcoal/skin.scss`. The editor's theme (body `data-ta-x-theme`, its Toggle Theme) can differ from the site's (`.page` `data-theme`), so the toolbar's styles must key off the editor's. On the staff edit page, `.page` stayed `dark` after the site's own toggle was saved as light and the page reloaded (cause unknown; it switched live when toggled back).
- **TinyMCE's `find` answers a Collection, not an array:** `editor.theme.panel.find('toolbar > buttongroup')` has `length`, indexes and `filter`, but no `some`, `map` or `find`; calling one throws in the page. `TinyMCECollection` in tinymce-api.ts types it so.
